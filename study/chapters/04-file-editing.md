# 第 4 章复习卡：找到生效代码，安全编辑，验证结果

原文：[改价怎样找对位置、保留已有修改并验对结果？](../../docs/learning/revised/file-editing.html)。例子：两件商品每件 100 元，普通价要从 200 改成九折后的 180，会员仍为 200。

## 一句话记住

**先沿用户实际入口找到生效文件，再基于刚读到的版本做唯一替换，最后从同一入口验证所有要求。** `Edit` 成功、函数单测通过，都还不能单独证明页面或结算正确。

## 1. 先定位“真正生效”的文件

知道文件名用 `Glob("**/prices.mjs")` 找路径；知道报错或页面原话用 `Grep` 搜内容；候选太多时缩小搜索目录。`RepoMap` 给结构线索，LSP 可查定义和引用，但最终要沿入口的导入关系确认。例子中 `shop/preview.mjs` 导入 `./prices.mjs`，所以预览使用 `shop/prices.mjs`，不是同名的 `examples/prices.mjs`。再看身份分支：普通顾客走 `standardTotal`，会员走 `memberTotal`。找到后用 `Read` 读原文；它同时记下路径、修改时间和文件大小，供编辑前核对。

## 2. `Edit` 怎样避免改错函数

若两个函数都有 `return count * price;`，只提交这行作为 `old_string` 会匹配两次，默认被拒绝。`replace_all=true` 会把两处都改掉，也不符合“会员不变”。应从 `Read` 中复制**不带显示行号**的原文，连同 `standardTotal` 函数头及必要上下文一起放进 `old_string`，让它在全文恰好出现一次。`new_string` 也要保留函数头、括号等未改部分，因为工具替换的是**整个匹配段**，不是自动只换其中一行。`old_string` 找不到时重读当前文件，不能盲猜位置。

源码：[`tools/edit_file.py`](../../src/ruocun/tools/edit_file.py) 的 `_edit_text` 用 `raw.count(old)` 检查匹配数量，构造替换全文后写入。

## 3. 旧文仍唯一，为什么可能要重读

假设同事在会员函数加了一行日志；普通价旧文没动，仍唯一。若存仍先比较上次 `Read` 记录的修改时间和文件大小与磁盘当前状态。变化时拒绝编辑，让模型重新读，以免它忽略别人的新改动。重读后如果普通价修改仍合适，`Edit` 在当前全文里局部替换，会员日志能留下。

这是偏保守的取舍：多一次读取，换取模型看过最新全文。该基线只用修改时间和大小，不能保证发现两个值都未变化的外部编辑，也不能锁住别的进程；所以后续差异和入口验证仍必要。整篇 `Write` 更容易因漏抄覆盖他人内容，局部改动优先用 `Edit`。源码：[`tools/paths.py`](../../src/ruocun/tools/paths.py) 的 `checkReadBaseline`。

## 4. 锁要包住“检查→读取→修改→写入”

两个 Agent 若从同一旧全文分别算出“普通 180／会员 200”和“普通 200／会员 160”，仅给最后的写入上锁，后写者仍可能把先写者改动覆盖。若存对同一路径用进程内 `fileLock`，把基线检查、读取当前全文、计算替换、原子写入、刷新基线放在同一临界区。共用 `ToolContext` 的连续编辑可看到刷新后的版本；不同上下文拿着旧基线的调用取得锁后会被要求重读。锁按规范化真实路径取得，只协调同一进程的 Edit；外部编辑器和独立进程不参加这张锁表。

保存时先写同目录临时文件，再 `os.replace` 到目标路径。这使目标路径切换更集中，但如果替换已成功、后续刷新失败，结果可能是“磁盘已变，回包未确认”；先查文件和差异，不要直接重做。源码：[`tools/paths.py`](../../src/ruocun/tools/paths.py) 的 `fileLock`、`atomicWrite`。

## 5. 验收要覆盖用户看到的入口

`Edit` 回包和 diff 说明哪段被替换；函数级测试的 180/200 说明函数在该输入下算对。但订单预览可能仍导入另一份文件，或把普通顾客送到会员分支。要用同一笔订单从**订单预览入口**分别走普通、会员路径，确认 180/200。若需求还包括正式结算，再从**结算入口**测两条路径；预览通过不能证明结算也走同一实现。

发现改坏时先读当前文件和差异，只撤回自己造成的错误片段；整份回退可能删掉同事后来加入的日志。修完重新从用户入口验证。

## 原文 7 道面经与设计题

1. **Coding Agent 怎样验证补丁，改坏了怎么办？** 沿用户入口找生效代码，检查 diff 是否只改目标，跑变化项和保持项；若错，读当前文件，只撤自己错误的片段，再从原入口回归。
2. **Agent 用了哪些工具？** `Glob` 按路径模式找文件，`Grep` 按文本找命中，`Read` 看原文并建立基线，`Edit` 做唯一文本替换；RepoMap/LSP 辅助理解结构与引用，Bash 可运行相关验证。
3. **明确报错按语义找不到怎么办？** 用原始报错文字做精确内容搜索，缩小到实际运行模块，再沿命中处的调用方和导入路径查，不只靠语义猜文件。
4. **old_string 带了函数头，new_string 为什么也要带？** 因为整个匹配段被替换。新文漏掉函数头，会把函数声明一起删掉。
5. **旧文仍唯一，为何要重读？** 文件可能在上次 Read 后被人改过；唯一只能定位旧段，不能证明模型已看过新内容。若存基线变化就要求重读。
6. **多个 Agent 改同一文件，如何防竞争？** 先识别共享资源；独立读可并行，写入按文件协调。若存同一路径锁住“检查基线→读取→计算→写入→刷新”，旧上下文冲突则重读。
7. **测试通过就能合并吗？** 要看测试是否走用户实际入口，是否覆盖不应变化的行为，并检查 diff 与别人修改是否被保留；直接测价格函数通过，不代表预览和结算正确。

## 额外追问

- **两份同名文件，能凭文件名选一份吗？** 不能；看预览/结算入口实际导入哪份。
- **为什么不按行号改？** 文件前面插入一行，行号就漂移；唯一旧文加上下文更能说明目标。
- **`replace_all` 什么时候用？** 只有用户确实要改全部匹配处，且逐处核对过影响时。
- **读写锁能防外部编辑器吗？** 不能；它只协调进程内同一路径的调用。基线和结果核查承担其余风险的一部分。
- **预览 180/200，结算仍为 200，结论是什么？** 预览验证只覆盖预览；继续追结算的导入、身份分支和同一笔订单的两条路径。

## 90 秒面试表述

“我先从用户实际入口定位生效代码。知道文件名用 Glob，知道报错原文用 Grep，找到候选后沿导入和调用链确认，不会只看同名文件。修改前 Read 目标文件，Edit 用一段唯一的旧文做局部替换；若两处公式一样，就把函数头也放进旧文和新文。若文件自上次读取后变了，若存会按修改时间和大小发现基线冲突，要求重读。进程内同文件编辑的锁覆盖检查、读取、替换和写入，避免仅锁落盘导致丢修改。最后从订单预览、必要时从结算入口验证普通价 180、会员价 200；函数单测或 Edit 成功都不足以代替入口验收。”
