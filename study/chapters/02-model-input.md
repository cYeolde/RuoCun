# 第 2 章复习卡：模型这次看到了什么

对应原文：[模型这次看到了什么](../../docs/learning/revised/model-input.html)。把作者的查价例子换成“查项目版本”也成立：模型要回答 `version = 1.2.3`，必须先在某条消息里真正看到这行内容。

## 一句话记住

**模型只知道本次请求实际带给它的信息。** 项目规则给行动方向，用户消息给目标，工具说明告诉它能请求什么，工具结果才提供刚读到的事实。

## 一次查价的两份输入

用户问普通价是否打折。假设 2 件商品每件 100 元：`count * price` 算 200 元，`count * price * 0.9` 算 180 元。价格只是练习材料，本章真正要看的是两次请求的差别。

```text
第 1 次模型请求
  messages: system（规则）、user（查价问题）、当前目录事实
  tools: Read 等当前可用工具的定义
  模型尚未看到价格公式 → 请求 Read

程序执行 Read，把 assistant 的工具请求和 tool 的真实结果存入历史

第 2 次模型请求
  messages: 原问题 + assistant 的 Read 请求 + tool 返回的公式 + 其他现行记录
  tools: 本次仍可用的工具定义
  模型看到公式 → 可以回答是否打折
```

`system` 通常承载程序与项目规则；真实用户的 `user` 消息给任务；`assistant` 保存模型回复或工具请求；`tool` 保存执行结果。若存还会用**带专门标记的 `user` 消息**装入程序生成的当前目录事实，所以不能只凭 `role=user` 就断言它是用户亲口输入。`tools` 清单与 `messages` 历史是两个不同字段：移除下一轮可用的 `Read`，不会抹掉历史里已读到的公式。

源码：[`agent/loop.py`](../../src/ruocun/agent/loop.py) 给本次请求设置 `messages` 和 `tools`，工具返回后写回历史；[`client/responses.py`](../../src/ruocun/client/responses.py) 负责 Responses 格式的调用与结果转换；[`tests/test_mvp_loop.py`](../../tests/test_mvp_loop.py) 检查结果回流。

## 哪些信息会更新，哪些不会

**项目规则是启动时读入的快照。** 若存默认读取用户级 `~/.ruocun/RUOCUN.md`，再从 Git 根目录走到启动目录，逐层读 `RUOCUN.md`、`RUOCUN.local.md`。旁支目录不会被读；找不到 Git 根时，只检查启动目录的项目级文件。若配置了兼容来源，也按 [`project_doc.py`](../../src/ruocun/project_doc.py) 的来源与层级规则插入。完全相同的**整份文本**才去重；子目录只多一句，整份文本就会保留。

运行中修改 `RUOCUN.md`，后来重新拼装首条 system，仍可能使用启动时保存在 `project_text` 的旧内容。想让当前会话知道新文字，可以显式 `Read` 改后的文件；那会作为工具结果进入历史。想让它成为新进程的起始系统规则，要重新启动并从相应目录加载。源码：[`agent/runtime.py`](../../src/ruocun/agent/runtime.py) 先调用 `loadProjectInstructions`，后面的 `system_prompt` 取同一份 `project_text`。

**当前工作目录则会按执行状态刷新。** 文件工具解析相对路径时使用 `ctx.cwd`。成功切换工作树后，程序在下一次模型请求前比较最近的目录记录；目录变化就把新记录接到历史尾部，目录没变不重复追加。该记录标有 `<ruocun-runtime-context>`，说明 `workspace_root` 与 `cwd`。源码：[`agent/context_runtime.py`](../../src/ruocun/agent/context_runtime.py)、[`agent/runtime_context.py`](../../src/ruocun/agent/runtime_context.py)。

所以，从 `shop/packages/pricing` 读 `prices.mjs`，切到 `shop` 后要改用 `packages/pricing/prices.mjs`。只在某次 Bash 子进程里执行 `cd`，不会永久修改会话的 `ctx.cwd`；后续独立的 `Read` 仍按会话目录定位。

## 你刚才那道题

**从 `shop` 启动，后来 `Read` 了 `packages/pricing/prices.mjs`，`pricing/RUOCUN.md` 会自动变成 system 规则吗？** 不会。启动时的规则链只到 `shop`；读取价格文件不会重新调用规则加载器，也不会自动扫描价格文件所在目录的规则。显式读取 `pricing/RUOCUN.md` 可以让模型通过 `tool` 消息看见内容，但它仍不是启动时注入的 system 规则。

## 原文面经与设计题（7 题）

1. **Agent 循环传给模型的消息分哪几类？** `system` 规则、`user` 任务或带标记的程序目录记录、`assistant` 回复/工具请求、`tool` 执行结果；可用工具定义另放在 `tools`。
2. **运行时怎样处理 AGENTS.md 这类项目说明？** 先说实际项目：若存默认找 `RUOCUN.md` 与 `RUOCUN.local.md`，按用户级、Git 根到启动目录读取，注入起始规则；文件改动不等于快照自动刷新。
3. **新请求需要带之前的用户话吗？** 需要相关历史。只有公式、没有原问题，模型不知道用户问的是普通价还是会员价。
4. **Bash 中 `cd` 后，下次 Read 从新目录开始吗？** 一般不会。那次 Shell 的目录变化属于该子进程；独立的 `Read` 仍用会话 `ctx.cwd`。
5. **刚改规则又重建 system，为什么还是旧要求？** 重建使用内存里的启动快照 `project_text`，没有重读磁盘。
6. **根与子目录都有相同规则，怎样处理？** 按清理后的**整份文件文本**去重，全文相同保留首次；多一句就保留两份，不做逐句合并。
7. **为什么把项目规范随请求发给模型？** 让模型在决定行动前知道项目约束，例如修改普通价后还要核对会员价。

## 面试官可能追加的追问

1. **给模型工具定义，是否等于已读取文件？** 不等于。定义只说明 `Read` 的名称与参数；文件内容必须由本地执行后作为结果送回。
2. **模型看见一条 `role=user`，就能认定是人发的吗？** 不能。若存的目录快照也用 `user` 角色，但带有专门标记和程序生成的路径事实。
3. **修改了规则文件，怎样证明模型真的看见新规则？** 看实际发出的请求里是否有那句话；不要只看磁盘文件或终端提示。
4. **工作树切换后，为什么把新目录放在历史尾部？** 最新目录事实要赶在下一次请求前进入历史；稳定的前缀可以保留，后续路径按新目录解释。
5. **从根目录启动后访问子目录，为什么子目录规则没自动进来？** 规则链在启动时决定，访问文件不是重载规则的触发器。可显式读取子目录规则，或从该目录重新启动。
6. **两层规则互相矛盾，加载器会自动解决吗？** 不会。它只按整份文本去重，冲突内容可能一起进入模型请求，需要明确规则优先级或人工澄清。

## 90 秒面试表述

“我看模型输入会分 `messages` 和 `tools`。第一次查价时，模型有系统规则、用户问题和 `Read` 的工具定义，但没有价格公式；程序执行读取后，把模型的调用和真实回包按 ID 配对保存，第二次请求才带上公式。项目规则是启动时按 Git 根到启动目录读取的快照，重新拼系统消息不等于重读文件；当前工作目录是另一类动态事实，工作树切换后会在请求前追加新目录记录。排查模型走错路径或漏掉规则时，我会先检查实际发出的请求，再核对工具执行时的 `ctx.cwd` 和规则加载时机。”

## 本章自检

闭卷说出第一次与第二次查价请求的差别；分别解释“规则文件改了”和“工作目录变了”何时被模型看到；回答为何 `Read` 子目录代码不会自动加载该目录的 `RUOCUN.md`。完成后进入第 3 章工具契约。
