新经验怎样产生

反思证据、筛选与受控积累

同一句“会员预览已修好”可能是自述，也可能背后有一组能对上的工具记录。受控积累关心的是下一次还能核对并复用什么。

01

测试通过后又改了代码，还能把做法存成已验证经验吗？

用户纠正模型，“以后预览与结算分开验，预览必须走 preview_total”。模型读取接口文件，修改断言并执行定向测试。测试通过后，又补了一次相关文件修改。此时模型提议把这次技术做法保存成有证据的项目经验。

首读自检 · 技术做法与用户原话各能留下什么？

用户纠错可以用用户原话作为来源，条件及做法仍需写具体。已验证技术做法缺当前版本证据，v12 对应 S1，不能支持 S2。重新核对 S2 并得到实际配对结果后才有相应证据。

最早的错误是把 v12 的退出码贴到后来出现的 S2 上。召回篇对照的是已有经验和今天的源文件。这里从另一侧接上，判断什么材料够格写成新经验。回合结束时，程序另发一次分析请求，从当前输入和工具结果里提炼可复用的做法。这一步常叫反思。分析模型给出的是候选，程序核对引用、文件版本和写入位置后才发布。

02

候选的证据包

2.1 从当前用户与配对工具结果提取证据

受控路径在完成且仍有效的回合末工作。它先取最后一条真正由用户发出的消息。程序生成的目录事实也可能用 user 角色入历史。学习模块和请求链共用 isRuntimeContext() 识别目录事实，检查角色和规范的消息内容。程序跳过已识别的快照，再从用户原话寻找纠错线索。用户明确说“纠正”或“以后统一”会成为候选线索。Read、Write、Edit 提供文件材料。验证证据沿原调用 ID 查回成功的配对结果，重复 ID 则无法唯一定位。助理的“测试通过”没有对应工具结果，不能作为这里的验证证据。

src/ruocun/agent/controlled_learning.py · 第 160–185 行

这里 identity 查回原 Bash 调用的命令，程序要求受支持的验证命令形状及成功输出。后台 BashOutput 还要能用运行 ID 连回原命令，且结果已退出并确认成功。Read 里的源码纵然包含测试字符串，也只能作为文件材料。线索规则是保守启发，表达含糊或命令形状不在识别范围时可能跳过，技术意义也要由具体断言说明。

2.2 原文摘录与来源资格由程序检查

有候选线索时，模型收到用户原文、工具证据与少量已有记忆摘要，输出提议的分类、标题、要点、适用条件、动作和引用。引用写成 {"id":"t4","quote":"…"}，这里的 t4 是证据包中的身份，仍能回到实际工具调用。程序要求每份候选引用 1 至 3 条，每个摘录是对应证据里的连续原文，并检查字段长度和疑似秘密。模型只负责提议，不能自行指定作用域、锁定或置信度。

src/ruocun/agent/controlled_learning.py · 第 285–309 行

引用当前用户纠正的原话时，来源记为 user_stated，稳定项目约定也可以走这个来源。技术做法必须同时引用文件与成功验证，绑定当前项目中可核对的实际文件。引用的成功检查不能早于有关文件材料和已观察到的编辑。文件证据创建候选的资格，待办、临时进度和无条件的成功宣称则没有这个用途。

03

验证版本与发布版本

3.1 验证边界为每个调用 ID 留一份来源快照

若等分析模型回答后才首次计算文件哈希，本例会把 S2 错配给 v12。RuoCun 在工具结果保存的观察边界捕获当下文件的内容哈希，按验证调用 ID 只记一次。即便没有捕获到可用文件，也保留空快照，后来重读同一条会话时不能补成当前版本。它观察此前已有工具证据的项目内常规文件，规模受至多 16 个文件、单文件 256 KiB 等限制。

src/ruocun/agent/loop.py · 第 436–440 行

src/ruocun/agent/runtime.py · 第 912–921 行

src/ruocun/agent/controlled_learning.py · 第 240–262 行

筛选时既检查证据顺序，也要求当前读到的文件哈希与至少一个被引用验证的快照匹配。现在改变开场里的一个时间点。编辑发生得更晚，候选通过初筛之后才动文件，也没有产生新的会话工具回包。用下图判断，单靠回看聊天记录，能不能发现这次变化？

核对候选还能否发布

不能将它发布为当前已验证做法。对话记录确实保留了成功凭据，可它的文件身份是 S1。只有在发布前读取当前文件，才有机会发现已变成 S2。

src/ruocun/agent/controlled_learning.py · 第 416–432 行

发布循环把磁盘哈希与候选的 source_hash 对照，还要确认其中一份实际验证快照也包含同一哈希。少了任一份便走 continue。「保留验证当时的文件身份，发布时重新核对同一版本」。这需要保存验证快照并重新读取来源文件。未能捕获快照的技术做法会少积累一些，哈希对得上也仍要核对实际断言覆盖什么。

3.2 发布只触及可核对的本项目自动条目

候选文本写入时带适用条件、做法和原文证据，保存为本项目的 semantic 记录。同名的普通条目、锁定记录或只读兼容记录会挡住自动覆盖。只有同时符合名称、标题和本地自动条目条件，才可能更新并保留创建时间和原使用计数。最后更新前还要比对准备写入时看到的旧版本。若那条记忆在这期间有人改过，就让这次写入停下。会话检查点也靠版本比对阻止旧结果覆盖新输入，此处保护的是单条记忆。

04

分析预算、取消与写入确认

4.1 只在有证据时发有限的分析请求

受控积累是独立选项，源码里的 CLI 默认 off。显式启用并符合交互条件时，单次启动至多安排 6 次分析。一次分析最多 12000 字符的提示与证据包，输出上限 1024 token，并关闭重试和工具，最多接纳 2 条记录，每条正文不超过 1800 字符。超长、疑似秘密和无法解析的候选被筛掉。附加请求用量记入模型账，受控分析未拿到用量或分析失败会暂停该启动后续自动学习，普通任务仍可继续。

src/ruocun/agent/runtime.py · 第 2046–2052 行

src/ruocun/agent/reflection_runtime.py · 第 137–158 行

代码在独立任务中运行分析，原回合在工具结果已配对的边界等待。沿用回合代次来判定返回的结果还归谁。例如分析属于第 12 代，在用户暂停而使第 12 代失效后才返回，就不能写到第 13 代里。取消信号也检查退出与原回合中断，走到写入前再核一次。这样可以在分析时放开工具锁，又能在写入前阻止迟到结果。

4.2 先保存候选状态，再登记写入意图

ready 只登记已备好的候选。真正动记忆文件时，再按执行前意图、执行后收据做两次记录。这次操作的类型叫 ReflectMemory，拿到可靠结果才可转 applied。已有可信收据就从收据继续，效果未确认就留在未决状态。「能重算候选，与能重放一次记忆写入是两件事」。

src/ruocun/agent/reflection_runtime.py · 第 94–120 行

这些关口证明经验候选可以由可追溯证据产生并受控保存。它们无法由一次顺利发布给出实际收益。观察同类任务在可比条件下是否少犯旧错、额外请求耗费多少、人工核对省了多少，才能回答自动积累值不值得开。

05

学习效果检测

5.1 核对经验候选的证据与发布条件

1．读流程 · 文件从 S1 变 S2，又变回 S1，但测试之后已有相关 Edit 记录，旧检查够吗？

展开详答

程序还检查证据中编辑与验证的相对位置。被引用验证早于已观察的相关编辑时，文件最终字节相同也不能用来跳过这一条件。找最后编辑后的实际验证。

2． 测试 v21 返回 0，当时没有捕获到被测文件的版本。随后文件被重新生成，Read 现在取得了它的内容哈希。有人要把这个哈希补给 v21，再保存为已验证经验。哪步缺证据，怎样补？

展开详答

v21 的成功回包能证明那次检查退出正常，缺的是验证当时对应哪版文件。今天的哈希不能倒填。确认当前来源和测试确实针对目标，在当前版本重新验证，取得新的调用、配对回包及观察到的版本，再考虑发布经验。

06

模拟面试官提问

6.1 Agent 开发实习

独立核心题

自动记忆为什么不把每次任务的总结都存起来？

展开参考回答

“能复用的经验要写出适用条件、具体动作和证据。任务过程往往只是临时进度。我们只给明确纠错、稳定约定和已验证做法一次候选机会。”例如用户纠错引用原话，技术做法还要引用文件和实际回包。

重点追问链

如何判断一次验证确实支持这条经验？

展开主问回答

“我会先找调用和回包配对，再查断言与来源版本。”

追问 1 助理写“已通过”够吗？

展开追问 1 回答

它没有配对的工具证据。

追问 2 实际命令通过后改过文件呢？

展开追问 2 回答

检查对应旧文件，需要最后修改后的证据。

追问 3 源文件未变能证明普遍正确吗？

展开追问 3 回答

它支持本条件下的观察，扩大条件需要另查。

6.2 Agent harness 岗位

独立核心题

为什么让程序保存分析候选和写入意图两类状态？

展开参考回答

“分析只产生数据。动记忆库才产生持久副作用，所以要另登记执行意图和结果。崩溃后需要判断从未动过、已确知结果，还是可能动过但无确认。”代码用 ready 与 scoped_intent 表达这两个阶段。

重点追问链

分析迟到或中途退出怎么安排？

展开主问回答

“把学习绑定到原工作代次，醒来和进写锁前都核对取消。可提交的结果还得过有明确身份的意图和收据。”

追问 1 分析完成时原代次已失效呢？

展开追问 1 回答

丢弃未应用结果。

追问 2 开始改文件后中断呢？

展开追问 2 回答

保留未决意图进入恢复。

追问 3 结果已确认但界面没显示呢？

展开追问 3 回答

使用可信收据续接确认后的步骤。

07

这一篇带走什么

受控积累从当前用户和真实工具证据提出经验，筛选来源、适用条件与版本后，沿独立的写入意图和收据发布到本项目。

  • 需要学习运行经验时，引用已配对的命令和结果，把文件版本记录在验证边界，发布前再核对。
  • 允许自动写入时，把来源、字符和次数限制放在程序关口，已有普通条目和锁定内容保留主权。
  • 把分析完成、持久写入确认与实际提效分开判断。写入不明时保留意图，质量与成本收益用可比任务观测。
