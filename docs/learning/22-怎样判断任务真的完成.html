怎样判断任务真的完成

验收证据、停滞信号与资源取舍

任务清单都勾了，Edit 成功了，模型也结束了。回到用户的那一句话，哪些事实已经能验收，哪些还缺一条结果？

01

待办都完成了，会员价为什么还是错的？

用户要求“订单预览新增九折会员价，普通用户仍显示原价”。模型改了一处价格函数，工具报告替换成功，待办全部变成 completed。它发出一段结束说明，回合返回 complete。交付前，用同一个 100 元订单分别走两种身份，得到下面的结果。

首读自检 · 哪条能报告通过？下一步该查什么？

普通用户预览检查通过。会员检查已经失败。先从页面追真实的价格调用入口，对照修改位置。定位后再改，随后重新跑两种身份的断言。

第 1 篇区分过回合停止与业务验收。现在要把需求拆成逐条可以核对的结论。会员预览的结果回答其中一条，普通用户预览回答另一条。编辑和回合的状态告诉你执行到了哪一步，不能直接填进这两行。

02

清单、工具回包与回合终态

2.1 TodoWrite 替换清单并给验收提醒

整份清单替换解决当前要记哪些待办。此处看写完后的提醒。当至少三项待办都勾完，回包提醒模型逐条回看需求，实质改动还要独立验证。检查是否真的运行，要另外寻找带实际结果的工具回复。

src/ruocun/tools/todo_write.py · 第 22–29 行

部分无人值守路径有“先列计划”的程序门槛：工具批出现名为 TodoWrite 的调用，便可标志这一门槛已跨过。清单内容能否通过工具校验、计划是否充分、要求是否做完，仍是后续核对项。用程序门槛约束最低行为时，要清楚它究竟观察了什么。

2.2 回合 complete 表示已保存回复且无后续调用

这次模型已经给出有效回复，空响应补救不再需要。程序保存助手消息，见到无后续工具调用就返回 complete。因此在这条分支里找不到会员预览的实测断言，它还需要实际执行。

src/ruocun/agent/loop.py · 第 411–421 行

「从原需求找每一条验收证据，不能用执行状态补缺口」。RuoCun 的系统提示要求逐条返回需求原文，对照读回结果或命令证据，非琐碎改动还要求安排 verify 并抽查报告。这个约定指导模型行动。complete 分支没有程序化验证任意业务目标的条件。

03

从改动范围到业务证据

3.1 差异核对位置，定向测试核对实际入口

先拿 diff 和重新读取的文件确认改到哪里。一次批量替换只有首处附近的差异片段时，另看实际修改总数和文件内容。回到页面的会员分支，发现调用的是 preview_total()，刚改的 settle_total() 只供结算。由此判断该修哪个调用路径，再用页面断言确认行为，避免为了复验不断重复检查结算函数。

需求或约束合适的证据本例现状
会员结算前预览为 90以会员身份调用订单预览入口，断言输出里的实际金额得到 100，失败
普通用户预览仍是 100以普通用户走同一入口，断言实际金额得到 100，通过
修改范围与需求对应查入口、读实际文件和差异，确认改动所在的模块当前只改了结算函数，待修正

修正后再用最新工作树重跑。涉及多个文件、接口或其它关键边界时，给独立核对方原需求、复验命令和实际产物，主代理按需要抽查其输出。子任务显示完成只是结束状态。测试环境缺失时，交付写“会员预览运行未验证”并说明已完成的文件检查。相关机制见 《文件编辑》 与 《重活交给子代理》。

3.2 只读 CSV 实录可以验收哪些条件

CSV 实录的最终回答有 EXPORT_TZ_UTC_OK。逐条回到工具结果，可以用首行 order_id,exported_at 核对表头，用唯一数据行的 2026-11-18T06:30:00Z 核对末尾 Z。模型取到了流程，读取了产物，给出的判定码覆盖这两项。

如果把验收范围扩大到日期格式和日历合法性，就要实际运行相应校验。只看末尾 Z 的证据不足以验收扩大的条件，生成端能否持续产出也要另作检查。

3.3 停滞提醒提示换一种更能分辨问题的动作

停滞提醒靠工具动作估计有没有推进。假设模型围着同一个旧函数读了几轮，这时可以用实际预览请求对照会员和普通用户，直接确定验收表里哪一项还有问题。若本轮借用了旧经验，按最后一次改动后的旧错检查核对当前入口和断言。提醒和经验都可以帮你找下一步，结果还要由证据来填。

04

累计用量、本次进程估价与边界停止

4.1 恢复的 token 与本次费用使用不同口径

每次服务返回用量时，addUsage 把输入、输出、命中和未命中 token 同时累加到账面总计与对应模型的用量桶。累计指标可能含恢复的历史 token，费用只用本次进程的模型桶按配置价格估算。如果当前输出“累计输入 25,000 token，本次进程费用约 0.08 元”，两个数字可能覆盖不同时间范围，不能拿 0.08 元去估算全部历史成本。

src/ruocun/session/session.py · 第 58–78 行

src/ruocun/session/session.py · 第 99–103 行

例如主请求输入 18,000 token，随后同一个模型又用 6,000 token 写反思。/usage 累计增加 24,000，/context 中上次主请求的输入仍是 18,000。addPrimaryUsage 在记账之外更新主回合读数和前缀缓存诊断，反思与摘要的用量只进入累计和费用计算。判断用途要看调用来自工具循环还是辅助步骤，单看模型名称无法区分。

src/ruocun/agent/context_runtime.py · 第 477–486 行

前缀篇的服务回报给出总输入和命中输入。现在把两类输入量和输出量分别计入成本，再核对两次工作实际验收了几项。成本是按本次进程与配置单价算出的估价，实际账单要用服务侧记录核对。

4.2 默认只提醒，显式硬预算在安全边界停止

MAX_BUDGET 提供有效的正数时形成费用阈值。到了回合内部的边界，程序先看 MAX_TURNS 限额，再看进程估价是否达到阈值。默认提醒后可以继续，显式 MAX_BUDGET_HARD=1 时先保存再返回 budget_limit；模型请求轮数先达上限时返回 turn_limit。它们描述不同停止原因，也与业务是否完成独立。

src/ruocun/agent/loop.py · 第 236–247 行

设阈值为 0.10 元，某轮请求前估价 0.08 元，回包记账后变成 0.11 元，完成工具批后还有事要问模型。到下一个轮次边界时，软预算提醒后仍可发下一次请求，硬预算先保存上下文再停止。如果轮数也正好用尽，源码先返回 turn_limit。这个例子给出预算真正能挡住的动作和已经发生的费用。

「边界预算能阻止下一轮继续，无法预先知道这一轮的最终费用」。跨过阈值的用量可能已经回报，硬停止的检查时点决定它控制哪个动作。停下时把表里已经通过、明确失败和未验证的事实留下，下次可以有针对性地继续。

4.3 比较推进方式时先用同一组验收条件

固定开场的两条验收条件。做法甲先扫所有价格模块，再跑广泛测试。做法乙直接追页面入口并跑两条定向断言，再补改动范围内的回归。假设得到这两组读数，先算各自有多少未命中输入，再判断哪组已覆盖本次需求。

核对未命中量，并判断能否直接用它们算费用

甲有 9000 × 40% = 3600 未命中 token，乙有 4500 × 60% = 2700。乙给出了两条行为通过所需的证据。这组材料还缺输出 token 和各类单价，无法给出总费用。比较真实收益还要固定任务、模型和验收条件，多次观察实际结果和开销。

05

学习效果检测

5.1 用目标和用量核对交付结论

1． 交付邮件说“100 行全部有效”。工具回执只显示读到了第 1 至 20 行，文件末尾尚未读取，助手已返回 complete。你会保留邮件里的哪部分结论，怎样补查？

展开详答

可以说明已读取前 20 行。仅有读取记录还没有校验结果，100 行的数量也要核对。按实际文件统计数据行并逐行跑约定校验，保存总数、失败行和文件版本，再据回执写交付结论。回合返回 complete 说明本轮已经结束。

2．读控制流 · 到边界时达到软预算且还没触发轮数上限，程序会返回 budget_limit 吗？

展开详答

默认不会。只有硬预算显式打开才会保存并返回 budget_limit。如果轮数也已先达到上限，这个分支之前会先返回 turn_limit。

3． 结课设计评审 用户要求导出的每行都是合法 UTC 时间，并在验收通过后向远端登记一条备注。现场只有正确表头和一行以 Z 结尾的抽样。另有一次备注追加已发出，回包超时，随后重连成功。请设计收尾流程，写三句交接说明，交代已验证的范围、暂缓的动作和接下来要取的证据。为什么值得多做这一步？

展开详答

我能确认表头正确，抽到的一行以 Z 结尾，其余行和日期合法性仍待验证。

我会暂缓再次追加，先按原调用 ID 核对本地记录，再用可对应本次操作的远端回执或审计记录查备注是否已写入，结果仍不明就保留未决，避免重连后重复登记。

我会从交付入口生成 CSV，逐行校验日期可解析且符合约定的 UTC 表示，记录文件版本、总行数和错误数，多花一次复验，才能据实决定补记、保留或更正那条验收备注。

6.1 Agent 开发实习

独立核心题

怎样防止模型把已完成待办当成验收？

展开参考回答

“让它重新打开用户原话，把每条要求配到能复查的结果。比如会员预览是否变成 90，要走目标入口断言，不能只看工具成功。”重要改动有条件时安排独立复验，主代理还要查看真实输出。

重点追问链

代码改完了，如何快速补关键证据？

展开主问回答

“先查实际使用的入口，再把相同输入和不同身份过一遍，核对需求提到的变化和保留项。”

追问 1 检查都在旧函数上？

展开追问 1 回答

把测试对准当前调用路径。

追问 2 相关服务无法启动？

展开追问 2 回答

保留文本核对，写明运行未验证。

追问 3 只看到下一次模型没有调用呢？

展开追问 3 回答

最多说明这次请求回合结束，应回到验收证据。

6.2 Agent harness 岗位

独立核心题

如何设计成本约束，又保证停止时的工作可追？

展开参考回答

“记录本次请求用量，分模型估算成本，在明确安全边界判断是否停止。默认可提醒，明确硬限就先保存。回报停止原因和已取得的证据。”历史累计 token 与本次费用需分别说明。

重点追问链

要评估一个新推进策略，为什么不能只比命中率？

展开主问回答

“先固定业务验收条件，再比较完成同一目标的资源开销。命中率是输入的一部分，也要看总用量和实际结果。”

追问 1 命中率高但用了更多 token？

展开追问 1 回答

看输入总量、未命中和输出，按同模型口径估价。

追问 2 成本小但结论漏了一项？

展开追问 2 回答

先补验收，不能直接宣称效率更高。

追问 3 恢复了历史会话怎么办？

展开追问 3 回答

比实验所需的实际用量或当前进程费用，明确历史成本缺口。

07

这一篇带走什么

RuoCun 用清单和回合状态推进任务，用进度信号和预算管理资源，最终交付仍要把原需求逐项对到实际证据。

  • 当操作已成功但目标可能没完成时，读回文件和实际差异核对位置，再从用户所用入口验证要求的行为。
  • 遇到停滞提醒时，挑一条能对现有假设给出不同结果的检查。勾选、提示或命令次数只能描述过程。
  • 比较方案时统一验收和计费口径，区别累计用量与本次费用。硬预算触发后按已确认结果交付，明确失败和未验证的条件。
