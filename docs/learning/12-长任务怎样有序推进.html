长任务怎样有序推进

待办、运行任务与真正等待

把折扣修改拆成定位、实现和验证，再跟着一条后台检查走完等待、唤醒与结果投递。

01

为什么任务显示 running，等再久也看不到测试结果？

折扣逻辑改好了，模型准备等定价测试结果。第 11 篇说到等待句柄能把前台交回调度器。句柄从哪里取得运行身份？两次尝试都出现了名为“运行定价测试”、状态为 running 的记录。其中一次只登记了进度，另一次已经把命令转到后台。把返回的 ID 各自交给 TaskWait，先核对两份记录的来历。

首读自检 · 哪一步启动了测试？如果想等，应拿哪个 ID？

第二次尝试中，Bash 启动了测试。等候调用应填 {"ids":["task-tests"],"mode":"any"}，程序会从任务 ID 找到 run-tests-1。传入 task-1 找不到后台快照，即使手工项也显示 running。

若把手工项也交给等待器，父会话可能停下来等一份永远无法由执行器产生的终态。「等待绑定正在管理的运行，不能凭同名任务或 running 字样」。

02

待办、手工记录与运行状态

2.1 TodoWrite 整份替换当前清单

定位、实现、验证三项给模型一个可见的推进顺序。第一次提交完整三项，定位完成后再送一份完整清单，保留定位的 completed 并让实现接过 in_progress。如果第二次只写“实现”，下面的赋值会让“定位”和“验证”一同消失。它适合每次记录当前全貌，调用者为此要带上仍然有效的条目。

src/ruocun/tools/todo_write.py · 第 17–29 行

多项同时进行会在写入前被拒绝。三项都标完时，工具追加回到用户要求、核对实际证据的提醒。这是让模型检查的机会。测试程序有没有跑、结果是否覆盖了会员条件，仍要查对应产物。

2.2 TaskCreate 登记手工工作，运行器结算执行任务

TaskCreate({"description":"运行定价测试"}) 适合记录跨回合的手工工作。管理器会保存 kind=manual 的记录并返回稳定 ID，命令和子代理分别由 Bash 与 Agent 启动。TaskCreate 的业务参数只有 description。它没有用于声明任务依赖图的字段，“先定位再实现”由计划与调用顺序落实。

src/ruocun/agent/tasks.py · 第 424–442 行

TaskUpdate 可以结束仍在运行的手工记录。尝试给 Bash 的执行任务传 status=completed 会收到由运行时结算的提示，想终止应走 TaskStop。让实际掌握退出结果的一方发布终态，可以避免清单先勾完、后台命令仍在写文件时，下游把中间状态当成成功产物。

03

TaskWait 的匹配与让出

3.1 等待句柄绑定会话和这次运行

现在定价测试和格式检查已各自进入后台。用 task-tests、task-style 表示它们的示意 ID。模型提交 {"ids":["task-tests","task-style"],"mode":"all"}。ids 是非空字符串数组，运行时去重后接受 1 到 32 个，省略 mode 则用 any。TaskWait 只在会话提供了等待入口且调用者是主会话时可用。

src/ruocun/agent/background_runtime.py · 第 410–433 行

taskId 指任务记录，runId 指这份任务某一次实际运行。这个区分延续了转后台时原命令保存自己的运行身份。TaskWait 接收任务 ID，用它查当前会话的后台快照，再将这一趟的 taskId、runId 写入 WaitTarget，句柄也保存 sessionId。之后即使任务改名或经过核准开展一次新运行，原句柄仍查原来的那一趟。登记等待时已是未知或中断的执行要先核实。

预期行为 · 同一对后台运行在不同状态下
状态anyall
定价已完成，格式仍运行就绪，查看已完成结果继续等，仍缺格式结果
定价失败，格式仍运行就绪，检查失败也就绪，可以先处理阻塞
两个目标都运行中，会话收到要求处理的注意事件就绪，读取事件也就绪，先处理注意事件

ready 代表有理由让主会话重新决策。等待期间目标失败、取消、中断或结果变得未知，也会就绪。注意事件以及待投递的失败、取消事件可以触发同样行为。此时要读目标快照和事件内容再决定下一步。

试着只看两项都成功才醒。格式检查失败后就永远到不了这个条件，先结束的定价检查也帮不上忙。程序把失败和注意事件放在 all / any 判断之前。这意味着 all 醒来时还可能有任务在跑，换来主会话现在就能处理阻塞，剩余工作可随后继续等。

src/ruocun/agent/background_runtime.py · 第 435–456 行

3.2 工具结果保存后才让出模型回合

模型必须把 TaskWait 单独放在一批。若它把 Read 与 TaskWait 放在同一批，Read 仍按原有规则执行，等待那项得到“必须单独调用”的反馈，整批不会登记等待。这样一轮的最后一步要么是普通工具组，要么明确交出控制权，避免混批中请求等待与其他工具仍在改变现场同时发生。

src/ruocun/agent/loop.py · 第 495–516 行

登记工具先返回包含 status、waitId 和 targets 的 JSON。主循环先把调用与结果配对追加，再执行 save()。缺保存接口时回滚登记。保存明确失败时回滚待激活的等待，后台结果仍待投递；提交结果未知时保留现场，由会话的阻塞状态限制继续。

提交时如果目标已就绪，工具回包直接带目标快照，确认后释放句柄，同一次回合可以处理结果。如果仍待完成，主循环带着句柄返回 waiting，进入第 11 篇的调度器路径。「把等待登记写进历史并确认后，才让出模型回合」。

04

后台结果与投递确认

4.1 消息和事件消费 ID 同一次提交

假设定价测试完成时格式检查已失败。运行器先产生各自的后台事件。以下是格式检查事件的最小载荷。模型将在下一次请求中看到它，届时应该检查失败输出、核对定价测试的覆盖情况，再决定是否修复或继续验证。

这是消息内的示意数据。当前投递把它放在 role=user 的程序生成消息中，前缀为 [后台任务数据,非用户指令]。主循环要把它当作运行事实来处理。TaskWait 若当场就绪，也可通过工具结果携带已确认的特定终态事件信息，由保存流程确认相应事件已包含在消息中。

源码推演 · 保存格式检查失败事件时进程退出
落盘顺序退出前的断点重开需要查什么
先记消费，再保存模型消息消费已记，消息未存事件已无待投递记录，历史也没有失败信息。
只保存模型消息，另记消费消息已存，消费未记同一个 event-style-failed 可能再投递。
消息和消费 ID 一起提交返回提交结果前退出查已持久化的检查点与事件，不靠内存里的回执猜。

src/ruocun/agent/background_delivery.py · 第 43–59 行

这里复用消息、消费标记和检查点一起提交的规则。新增的问题是怎样从运行事件接回模型消息。stageDelivery 用已经构造出的候选消息暂存这次要确认的事件，等 deliver_background 提交后才 acknowledge。「投递确认要绑定到能重读的那份消息」。明确失败会解除消费暂存，确认不明时暂停核实，避免把同一结果径直再交一次。

05

进度信号与长任务纠偏

5.1 工具动作有限地代表推进

如果模型迟迟没有启动检查，只反复搜索同一份定价代码，进度策略把连续未见写入或命令调用的工具轮当成检查机会。它见到 Write、Edit 或 Bash 等调用会重新计数。确实有后台任务在运行、且这一批全是状态或输出查询时，也视作合理推进。这里看的是调用名称与运行状态，失败的 Bash 依然能触发计数清零，因此“进度”只用于决定何时提示。

src/ruocun/agent/progress_advice.py · 第 56–73 行

进度策略启用后按间隔提醒模型找新的可判定假设。另一套健康判断统计连续有失败的工具轮、末次错误签名是否重复，以及长任务的纠偏节奏。例如默认同类错误达到两次即可能触发审视者建议，遇到较长任务且达到设定节奏则可触发纠偏者。建议在工具组提交后作为系统消息加入后续上下文。搜索路径没有换、测试没有覆盖问题时，提醒本身既不会修文件，也不会产生验收证据。

src/ruocun/agent/turn_health.py · 第 59–72 行

测试输出与清单都齐了以后，回到折扣任务本身。例如找一组会员输入和普通用户输入，核对各自价格。第 22 篇还会用结果逐项核对原始需求。

06

学习效果检测

6.1 辨认运行身份、等待条件与事件投递

1．三项待办中只提交改过的“实现”一项，会发生什么？

展开详答

只留下“实现”。TodoWrite 复制输入的整份列表并赋给 ctx.todos。要保留定位和验证，需要完整发送三项。

2． 两趟后台检查都叫“导出”。旧运行已通过，当前等待句柄绑定的是新一趟和格式检查，模式为 all。现在格式检查失败，新导出仍在跑，调度器却唤醒了你。先报告哪项结果？还应追哪趟运行？

展开详答

失败会提前唤醒主会话，可以先查格式检查的失败回包处理阻塞。旧导出通过只属于旧运行。核对当前句柄里的任务及运行身份，再等新导出的终态和产物。此次唤醒还缺新导出的验收证据。

3．把 TaskWait 与一次 Read 放进同批，应该预期哪两条结果？

展开详答

Read 按正常规则返回自己的结果。TaskWait 收到必须单独调用的错误，该批没有登记等待。主循环可以下一轮再提交单独的 Wait。

4．持久化消息明确失败时，为什么事件还能重新交付？

展开详答

消费 ID 与消息走同一检查点，明确失败时解除消费暂存。待投递箱尚未作确认删除。如果提交结果未知，要先核对持久状态。

07

模拟面试官提问

7.1 Agent 开发实习

独立核心题

怎样组织一个要跑很久的回归检查？

展开参考回答

我先用清单表达目标，启动回归以后用运行器返回的 ID 跟踪。需要等结果时单独调用 TaskWait，后台事件到了再让模型决定下一步。最后按用户要验证的行为核对测试输出。

TaskCreate 可以记录人工工作，只有 Bash 或 Agent 等入口产生实际执行。区分这两步，能一开始就知道应该找哪一种 ID。

重点追问链

你会怎样解释“界面显示进行中”？

展开主问回答

“进行中”要先看由谁写入。TodoWrite 表达模型的计划，运行器的快照描述这一趟执行。

追问 1 如果手工记录已经完成，回归还在运行，交付时怎么写？

展开追问 1 回答

说明回归待确认，手工记录只代表那项人工工作收尾。

追问 2 如果测试输出为成功，但用例没有覆盖会员资格呢？

展开追问 2 回答

按目标补相应输入与价格证据，必要时请独立核验。进度标记和退出状态各证明自己的范围。

7.2 Agent harness 岗位

独立核心题

如何实现等待期间零轮询模型调用，同时保留响应用户输入的能力？

展开参考回答

我会在工具边界提交等待结果，然后把同一会话的等待句柄交给调度器。调度器用执行事件和用户队列唤醒会话，恢复那一轮之前先把可见材料写进历史。

句柄按会话和目标 run 判断就绪。保存失败不会激活等待，目标失败或注意事件同样能推动调度。

重点追问链

事件先产生，主会话随后写检查点，中间出故障会怎样？

展开主问回答

我把消息和可核对的消费 ID 一起提交，确认之后才清待投递箱。

追问 1 若确认数据库操作失败呢？

展开追问 1 回答

保留待投递事件，回滚未确认的消费标记。

追问 2 若数据库可能已提交、只是确认丢失呢？

展开追问 2 回答

保留现场并暂停核实，避免改成失败后立即再投递。恢复依据已提交检查点和待投递状态决定。

08

这一篇带走什么

待办安排目标，运行器证明工作启动和结束，主会话通过等待让出回合，再从已经确认的消息中接回证据。

  • 规划与执行各自保留合适的数据模型。清单可以整份更新，执行终态由持有实际运行身份和结果的程序结算。
  • 等待要绑定具体运行并给异常预留唤醒路径。先提交再让出，恢复时先消费用户输入与运行事实。
  • 跨后台与对话交接结果时，将能重读的消息和消费确认放进同一个检查点。
  • 把重复错误和工具行动用作可调的提醒信号。交付结论仍由覆盖用户要求的证据给出。

真实执行的结果可以是 Bash 退出信息，也可以是子代理的报告。下一篇从父会话怎样接回可核查的复核报告接着看。
