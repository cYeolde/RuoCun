命令运行很久

前后台交接、输出回查与取消确认

沿一次价格检查追踪命令的身份、日志和终态，判断什么时候该等，什么时候可以验收。

01

看见第一条日志，就可以说检查通过了吗？

上一章用一次很短的试算核对了两个价格。假设现在要跑范围更大的 check_pricing.py，它先检查普通商品，最后才检查退款边界。模型调用 Bash 开始检查。程序把启动的进程、它的日志及退出状态登记成一次运行，也就是一个 run。下面用绑定了可恢复 Shell 后端的 Windows 会话追这次运行。

下一次调用该填什么？目前能确认整个检查通过吗？

查询用 BashOutput({"id":"run-price-7"})。第一条 PASS 只覆盖普通商品，原命令还没有退出。继续沿同一个 ID 等终态，才知道退款检查和这次命令的最终结果。

继续沿该 ID 查询。假设下一次拿到下面的工具回包节选，现在才知道这次检查最终失败。

第一次 Bash 和后来每次 BashOutput 都是独立工具调用，各有调用 ID，按第一篇的规则同回包配对。查询参数中的 run-price-7 则始终指向同一次命令执行。只留下聊天里的半截日志，后续就失去了查这份运行的位置。再跑一次会生成新的 run；如果两份执行同时写报告，已经无法单靠报告内容判断是哪一次产生的。

02

前台执行与结果

2.1 执行计划确定命令的真实运行条件

command 是实际传给 Shell 的命令，description 为审计提供语义说明。background 省略时按前台运行。处理器先取当前 ctx.cwd，缺省用 workspaceRoot，再构造执行计划并应用沙箱决策。工具名叫 Bash，Windows 默认实际用 cmd，非 Windows 的默认执行器是 /bin/sh。显式调用其他解释器时，计划与裁决要看实际方言。

src/ruocun/tools/exec_shell.py · 第 138–151 行

在绑定受管后端的 Windows 会话，执行交给 managedShell.execute。前台有实时 stdout（常规输出）和 stderr（诊断输出），输出回调发生异常时只关闭回调并记录提示，执行器仍继续收取结果。在普通前台后端里，等待者被取消时先设执行信号，再等待由原命令和它启动的子进程组成的进程树退出。前台回包最后包含两路输出、退出码或中断状态及耗时。

src/ruocun/tools/exec_shell.py · 第 182–191 行

src/ruocun/tools/exec_shell.py · 第 198–208 行

第一条 PASS 可以给用户看，最终判定还要看退出码及这次检查覆盖的内容。即使实时界面失去更新，也可以等工具的最终回包。后端把本次是否失败单独交给批执行器，正文里的旧退出码不会改写本次状态。「实时输出负责观察，退出收据才负责确认命令的终态」。

03

前后台交接

3.1 先保存后台决定，再交出原 run

前台时，原来的 Bash 调用继续等命令结果。转到后台后，命令继续运行，模型可以拿到 run ID 等通知或查询。可以从一开始请求 background: true，也可以由终端把正在前台的执行转过去。前者对新 run 做交接，后者取当前前台的 run，交接期间排斥另一条前台取消路径。两条路都保留原执行器、输出文件和控制身份。后端缺失时，显式的后台请求会得到命令未执行的反馈。

src/ruocun/tools/managed_shell.py · 第 570–590 行

设想界面一收到“转后台”的按键就解除前台责任，而后台的执行器还没确认接手。这时控制器退出，重开只记得界面请求过交接，无法证明这次命令是继续运行还是已经退出。对照上面的代码，run-price-7 尚在运行时，管理器先保存 detach_requested，再等原 runner 确认保留，才提交 detached=True。这多了两处状态落盘和一次往返，让重开时能分辨“已提出交接”和“交接已确认”。若原命令恰好退出，交接前或通信失败后都可用原运行的终态收据接回结果。收到后台回执以后，管理器还能将完成事件交给后台运行系统。需要让出回合等待具体事件时，见待办、任务与等待。

3.2 重启后用原材料接回日志和控制

src/ruocun/tools/managed_shell.py · 第 788–804 行

会话加载按已保存的运行目录、签名清单和 run 身份核对恢复材料，还会核对 runner 控制租约的代次。能验证终态就导入终态，能接管仍在运行的后台 runner 就接到原 run。恢复发现 runner 未完成启动认领时不会补发启动。非终态材料缺失或身份核对失败时，状态保留为 unknown，原日志和现场仍可供后续定位。「恢复运行要找回原身份，重新启动会得到另一次执行」。

04

输出窗口与日志回查

4.1 用输出游标取新内容，再按位置找完整日志

BashOutput 接收后台工具返回的 id，管理器分别维护标准输出和标准错误的读取游标，终端实时显示用另一组游标。这样终端先看到一行，工具查询还可以收取那行。模型连续查询同一个 running run 且没有非空新增时，处理器有 30 秒的提示节流，引导等待完成通知。

src/ruocun/tools/managed_shell.py · 第 465–486 行

某次查询可能遇到 35,000 个 UTF-16 单位的新增 stdout。模型侧窗口超过 20,000 个单位时返回首 12,000 和末 8,000 个单位的预览，边界避开拆开代理对，再附日志目录。退款失败细节若在中间，应该按回包给的目录和 stdout.txt 或 stderr.txt 回查相应位置。问一次 BashOutput 就推进游标，下一次调用只从新位置读。

src/ruocun/tools/exec_shell.py · 第 79–95 行

前台最终文本还有自己的长度限制。例如汇总内容为 20,000 个 Python 字符，_spill_output 留前 9,600、后 6,400，省去中间 4,000；写入经过检查且成功时，附上 .ruocun/spill/ 下的完整汇总文本路径。这里的“完整”指这层收到的文本。受管前台收集也有自己的上限，超出时要以 runner 的两份原日志为准。回包出现何种路径，决定 Read 或 Grep 下一步要查哪里。

05

取消请求与退出确认

5.1 取消进入 canceling，收据确认后进入终态

如果退款测试持续卡住，已知 run ID 可以交给 KillShell 请求终止。控制器先查当前终态及控制材料；已核对身份的运行可以收到取消，材料无法核对时保留现场，避免用一个可能已被替换的进程身份盲目干预。

在哪一次可以确认运行结束？能说明是取消使它结束的吗？

第二次才有同一 run 的可信终态。收据表明检查失败退出，程序可能在取消到达之前已经失败结束。第一次只证明系统已登记取消意愿。

src/ruocun/tools/managed_shell.py · 第 663–679 行

cancel_requested=True 和 canceling 记录请求阶段。终态收据是 runner 为这次执行写下的退出证据。它要签名通过、执行身份一致，runner 对外状态与收据的终态和日志元数据匹配并标明关闭。退款检查可能在请求到达之前已经失败并退出，这时按收据读作失败退出。工具 BashOutput 将 completed、failed、canceled 都显示为 exited 并附退出码，判断取消是否生效要查受管运行实际终态。

src/ruocun/tools/managed_shell.py · 第 167–180 行

这份收据回答进程是否退出。工具批次还能否把真实结果补进原调用，需要另外核对会话保存的进度，见意图和回包的持久化。命令本身如何配合会话等待，见用实际运行身份登记等待条件。

06

学习效果检测

6.1 按日志和收据判断结论

1． 夜间检查有两趟。昨晚的运行 old 已退出，退出码 0。今晚的 new 刚打印“索引检查通过”，后台状态仍为 running，余下还有一次导出检查。交接时能报告哪项进度？下一步按哪个 ID 查什么？

展开详答

今晚只观察到索引检查的通过日志。昨晚的退出码属于另一趟运行，今晚的导出检查还缺结果。保留 new，等该次完成通知或用 BashOutput 按该 ID 查新增输出，核对最终状态、退出码与导出检查的实际结果。

2．BashOutput 显示输出被截断，Grep 应该搜索哪份数据？

展开详答

依据返回的日志目录找对应的 stdout 或 stderr 文件。前台最终输出如果只给出落盘文本路径，先识别它是前台汇总还是原 runner 日志。下一次增量查询不会自动补回已经略去的中段。

3．发送取消后控制连接中断，找不到可验证的收据。恢复后可否直接重启检查？

展开详答

保留原 run 为结果未确认，先依据运行身份和材料核实。重新启动会创建新的执行，原检查的产物可能已写出。已有可信终态时导入该终态；能接回后台时继续查原 run。

07

模拟面试官提问

7.1 Agent 开发实习

独立核心题

你怎样给用户展示一个仍在运行的命令？

展开参考回答

我会展示实时日志和当前状态，让用户知道系统仍有进展，再单独展示最终退出和检查内容。转后台时把原 run ID 给后续查询。这样先看到一行通过不会误报整项检查结束。

实际依据是执行器的输出回调和 Bash 最后由 stdout、stderr 与退出信息合成的工具结果。

重点追问链

日志太长怎样找到失败原因？

展开主问回答

先看头尾摘要，再按落盘指针查缺失的中段。展示层不用把完整日志塞给模型。

追问 1 改为后台后长日志如何查看？

展开追问 1 回答

后台时按原 run ID 收增量，预览省去的部分到对应的 stdout 或 stderr 文件定位。

追问 2 后台查询一直没有新增又怎么办？

展开追问 2 回答

空输出时参考当前状态，正在运行就等待完成通知。需要在会话里明确等待时登记已知后台任务的等待条件。

7.2 Agent harness 岗位

独立核心题

前后台交接时，如何处理改变执行责任与程序退出之间的竞态？

展开参考回答

我把交接视为原运行的一次状态转换。先持久保存转后台意向，等 runner 确认保留原运行，再把控制从前台责任移出。前台取消与这个过程用同一个控制锁协调。

detach 在交接前和通信失败后都检查终态收据，处理原命令恰好已经退出的情形。

重点追问链

重启后原 runner 仍在，该怎样接？

展开主问回答

用保存的 run 身份、签名材料和控制租约核对再接管。保留同一个 run，避免产生第二次执行。

追问 1 若收据已生成但未确认发布呢？

展开追问 1 回答

核对已发布的 runner 终态、日志和关闭信息。不满足条件时继续核实或保留未确认状态。

追问 2 取消消息已发、终态始终没回来呢？

展开追问 2 回答

取消消息只表明有人请求终止。一直没有可验证的结果，保留原现场，明确结果尚未确认。关联意图、结果确认与恢复。

08

这一篇带走什么

一条 Shell 命令从前台执行到后台跟踪始终沿同一个 run 交接，日志按游标收取，最终由退出信息或受管收据确认终态。

  • 后台运行需要稳定身份、可回查输出和可重接控制；交接失败后用原身份核实，避免再启动一次并发写产物。
  • 长输出进入模型前先保留必要预览；若需要确定中间发生了什么，就按实际返回的日志位置回查。
  • 取消要保留请求与退出两个阶段。控制失败或材料不全时保留现场，等真实收据再发布确定终态。

本篇从命令获准并启动后开始追踪。下一篇往前一步，看程序拿到批准时，怎样确认这次操作还有资格开始。
