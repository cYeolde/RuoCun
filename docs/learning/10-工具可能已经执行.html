工具可能已经执行

意图、结果确认与恢复

用一次写盘后的中断，看清文件已改、工具结果已确认和模型下一轮能看到结果之间的距离。

01

磁盘上已经是“九折”，重开后还要再 Edit 一次吗？

上一篇的断流示例里，Read 还未派发。这里把中断往后挪：用户要把 pricing.txt 中的“普通价”改成“九折”，模型的完整响应已保存，里面有编号为 call-price 的 Edit，程序有机会实际写文件。重开时对话尾部只有这条调用。此时先看执行账本，也就是程序在会话历史之外保存的工具意图和结果。

哪一种能给 call-price 补回原结果？另一种下一步该做什么？

B 有该调用的已确认结果，按 call-price 原样补回即可。A 只证明意图已登记，即使文件看起来改过，也缺少这次工具运行的已确认回包。保留未决，核对实际状态后决定如何继续。

只看对话尾部的做法会把 A、B 都当作工具没跑过。若原操作是往报告里追加一行，就会在已经追加过的报告里再写一遍。只看文件现值也无法给 A 造出可信的回包，文件可能在这个调用开始前就由别的操作改过。执行身份和结果一起保存，恢复时才知道哪条原记录能补。

02

工具意图与已确认结果

2.1 先提交执行意图，再进入处理器

沿派发前对参数、权限和取消的检查往下走。编辑获准后，会话构造一条 Intent，把工具身份、最终参数摘要、批准记录引用和 owner_epoch 一起入账。这里的 owner 是有权提交当前会话数据库写事务的程序实例，接管数据库时持有版本 owner_epoch 递增。主会话的工具引用写为 ToolRef("main", call_id)，子执行用自己的范围，避免同名调用 ID 互相覆盖。

src/ruocun/session/conversation.py · 第 551–564 行

派发等存储提交回执后才进入处理器。意图提交失败时，本次 Edit 不进入实际写入。已有同一身份的意图时，存储先核对其最终参数与授权等内容，再决定能否复用 result_committed。身份相同而内容不同需要报冲突。

src/ruocun/session/durable_store.py · 第 734–748 行

代入现场 B，存储按工具身份找到相同意图，result_committed 分支直接把已确认结果交回派发器，处理器完全不用再跑。代入 A，started 只说明先写下了执行意图。从落盘到写文件之间，进程可能在进入处理器前退出，也可能刚写完还没落结果就退出。存储无法单靠这行记录分辨。RuoCun 接受了部分其实未执行的调用也要人工核实的代价，避免把可能已发生的副作用重做一次。「意图记录证明工具可能已经开始，已确认结果才能用来恢复回包」。

2.2 确定拒绝能回流，结果未知需要停住

Edit 确定找不到 old_string 时，通过 ToolRejected 回给模型明确的错误，模型可以重新读取目标。处理器意外异常可能发生在写入之后。对具有持久副作用的工具，派发把这一路升级成 UnknownToolOutcome，结果保存异常时也采用同样处理。普通读取出错可以回读失败文本。程序保留这几条不同路径，下一步才有正确依据。

src/ruocun/tools/tool_batch.py · 第 304–323 行

成功保存工具结果后，批次将文本包装为 role=tool、tool_call_id=call-price 的消息；批次结果按原呼叫顺序写入会话。由此形成两个提交点，一处确认单次工具结果，一处将结果写入下一次模型可见的历史。出现 UnknownToolOutcome 时主循环直接返回 outcome_unknown，不发下一次普通模型请求。

03

恢复视图与人工核实

3.1 从 journal 补配对，保持已执行操作的原身份

启动恢复时，存储把仍处于 started 的记录标成 outcome_unknown。已确认的结果继续保留。若有未决工具、运行或附件，会话保留阻塞状态；可以先查询恢复视图。阻塞解除后修复历史，按照助手原始调用列表找同一作用域的工具记录。

src/ruocun/session/recovery.py · 第 60–71 行

补配对有三种实质。已经配对的消息原样保留；有已确认结果就用该结果补同一个 ID；已保存调用却缺执行意图时可以补“未执行”。只要未决操作仍在，普通回合不继续，给一个新 ID 同样不能绕过未决状态。受管 Shell 可先尝试核实原 runner 的可信材料，避免把仍能恢复的原执行误判为需要重做。

现有 REC-05 自动验证覆盖了这些切点。保存意图后中断，文件保持原文。文件替换后、结果保存前中断，文件已有新内容。两次重开都保留未决。结果确认后、配对前中断则可以补回结果。从这组观测能看到，内置文件写入和数据库提交分属两个边界，中间有无法靠数据库单独确认的区间。

3.2 人工说明进入原记录，继续运行要有明确决定

针对 call-price，用户可查询 /recovery，按未决条目的作用域和 ID 核实文件现状与期望差异，再用 resolve 提交说明。原记录保存“用户处理未决操作”及其说明，区别于工具原始回包；decide 用于核实运行终态。恢复决定与消息一起提交，同一个决定身份重复提交相同内容可以取得原回执，内容冲突则拒绝。要继续受支持的普通子代理，还需明确的 continue 决定和可验证材料，并使用新 run，详见子代理章节。

示意中的 call-price 属于主会话。用户核实原记录后，可在若存的会话中提交以下决定。

04

检查点与取消收尾

4.1 数据库提交后才发布新 revision 和投递状态

会话检查点是一份可从磁盘恢复的完整进度，记录模型消息、已接纳输入、后台事件投递等状态。每次成功提交更改，就分配新的检查点版本号 revision。想象后台验证结果基于第 7 版准备，用户输入“保留日志”却先提交成第 8 版。同一个数据库所有者也可能持有两份不同时间的快照。

若直接覆盖，先丢哪条记录？若要求版本一致，后台事件现在算投递了吗？

直接覆盖会抹掉“保留日志”。按版本提交时 8 != 7，事务拒绝本次覆盖，数据库也没有在本次事务中确认后台事件已经投递。

Conversation 在检查点锁内为本次变更构造完整候选，由单独的存储工作线程串行提交。数据库在事务里核对 owner 的实例身份和 owner_epoch，再查 expected_revision 是否等于当前版本。前者挡旧进程继续写，后者挡同一进程的旧快照覆盖已更新的状态。检查点、发给模型的消息和已消费的后台事件标记使用同一个事务，保存成功要一起生效。

src/ruocun/session/durable_store.py · 第 1201–1220 行

src/ruocun/session/conversation.py · 第 467–482 行

如果后台消费的保存已明确失败，可撤销这次暂存消费，让事件仍待投递；如果等待被中断且提交结果无法确认，则阻塞普通推进。只有拿到回执才确认消费、发布 revision 和接纳输入列表。「会话以已确认的检查点推进，等待被取消时先核实存储是否提交」。

05

学习效果检测

5.1 为不同故障切点选恢复依据

1． 周报末尾已有“已核对”。重开时，主会话 append-8 的账本只有 started，另一趟执行恰好也有名为 append-8 的成功结果。现在能用哪个结果补主会话？还要查什么，再决定要不要追加？

展开详答

两次操作属于不同执行范围，另一趟的回包不能配给主会话。主会话账本只能证明它登记过意图；相同文字也可能原本就有。按主会话和调用 ID 查恢复记录，再核对可识别本次追加的版本、差异或审计记录。证据仍分不清就保留未决，交由人明确决定下一步，避免重复追加。

2．历史只留下助手发出的两个 ID，journal 两条结果都已确认。恢复后消息用哪个 ID，按什么顺序？

展开详答

查同一作用域的 journal，用助手原先的 ID 补配对，每条结果跟着原呼叫列表顺序写入，以便模型获得结构完整的历史。不需要重新执行工具。

3．旧副本基于 revision 10，权威检查点已到 11。请求还是当前 owner 发出，需要检查什么？

展开详答

仍需拒绝该旧候选。owner 说明谁有资格写，revision 说明它基于哪一版，二者各挡一种冲突。随后从可信检查点重新构造合法变更。

06

模拟面试官提问

6.1 Agent 开发实习

独立核心题

用户说文件看起来改好了，系统却报结果未确认。你会怎样解释？

展开参考回答

文件状态和工具回执分别保存。文件有可能已经被工具写过，但工具结果因进程中断没有确认。我会先核对原调用和差异，向用户说明事实，再提交核实结果。直接再跑容易给重复副作用留下机会。

实际判断从同一调用的 started、result_committed 和原文件状态出发。

重点追问链

文件没变化怎样判断？

展开主问回答

查看有没有意图。仅凭文件没变化，无法确认有意图后的全部过程。

追问 1 如果结果已经提交呢？

展开追问 1 回答

从 journal 按原 ID 补回结果，不再次执行。

追问 2 如果发现本次只是明确的 Edit 匹配失败呢？

展开追问 2 回答

把确定拒绝反馈给模型，读取新的原文后修正参数。关联文件编辑。

6.2 Agent harness 岗位

独立核心题

怎样设计恢复，让数据库和外部副作用之间的中断可解释？

展开参考回答

我会先用持久化的操作身份记录意图，再调用外部执行器，拿到结果后另行提交。恢复以确定的证据为界，完成结果可以复用，意图存在但结果缺失先标未知并停住。

RuoCun 的 ToolRef 区分执行范围与调用 ID，journal 的已确认结果可以用来补历史配对。外部动作和 SQLite 写入分属不同原子域。

重点追问链

检查点回执在取消时丢了怎么办？

展开主问回答

用操作 ID 和权威存储核实。回执不明时暂停继续，不能把它当作明确失败后再次覆盖。

追问 1 旧所有者迟到写入怎么办？

展开追问 1 回答

事务内核对 owner 与代次，同时核对期望 revision，挡住旧所有者与旧快照。

追问 2 用户重复提交同一恢复决定会启动两次吗？

展开追问 2 回答

相同决定只有一份持久记录。重复取回回执；同 ID 不同内容冲突。新 run 的派发须等继续许可提交。

07

这一篇带走什么

一次工具执行从持久意图进入真实处理器，确认结果后才写回模型历史，恢复与取消都要沿这些提交点找证据。

  • 需要恢复的副作用要有稳定操作身份。已有确认结果就按原 ID 复用，只有意图时先核实，防止自动重放。
  • 用一个检查点保存相关的输入、消息和投递状态，确认后再发布。owner 校验挡旧进程，revision 校验挡旧视图。
  • 取消后仍要收取已开始动作的结果。拒绝、确定失败、结果未知分别给出证据和处理路径，让后续动作有依据。
