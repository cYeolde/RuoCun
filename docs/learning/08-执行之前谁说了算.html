路径、模式与批准裁决

用同一个 Edit 分别走过参数、计划模式、授权和路径关口，找出真正让写入发生的条件。

01

参数都对了，为什么文件还没改？

上一章的命令已经启动，取消后要查它的终态。现在把取消提前到工具还在等待批准的时候。你在 /shop 里把商品标签从“普通价”改成“九折”。文件已经读过、只有一处匹配。工具调用 edit-42 参数齐全，命中需要人确认的规则。你打开批准框，程序还在等。

哪个现场允许继续检查写入条件？另一个现场能确认文件没被这次调用修改吗？

A 仍有资格继续检查路径和编辑条件。B 在批准返回后先发现取消，给 edit-42 记未执行的取消反馈，处理器没有开始。这个结论依赖本例中取消早于处理器启动。

只读批准表的实现会给 A、B 同一个决定，甚至在你取消后开始写文件。这里需要在批准返回时读一次实时状态，等执行意图保存完、真正进处理器之前还要看一次。多过这道关，换来晚到的同意无法替已经取消的回合启动新操作。

02

调用授权

2.1 用最终参数匹配 deny、ask、allow

本篇有三层状态。normal 和 plan 是当前会话的执行阶段，决定此时能否尝试写入。权限策略把工具名和参数判成允许、询问或拒绝。需要人工确认时，再由人对眼前这一次调用作决定。开篇的两张批准表都同意，变化发生在会话的实时状态。

权限运行时拿到工具名、实际参数和工具的 capability。Edit 的 capability 是 write，因此规则匹配会考虑实际工具与目标，随后还要结合当前模式和风险判断。这里把三种结果理解为拒绝、等决策和允许进入后续阶段。

src/ruocun/permissions/rules.py · 第 169–175 行

以普通文件工具为例，同时命中拒绝和允许，evaluate 先返回 deny；匹配 ask 的调用交给批准流程。规则判断之外还有默认决策。如果是自动权限模式，普通且符合条件的 Edit 可以放行；明确要求询问的规则、危险性和敏感目标会改变决策。无明确规则的侧效应调用在非自动的普通策略下通常需要询问。所以会话模式 normal 要和选中的权限策略一起读。Shell 还要根据命令实际执行计划和方言分析参与裁决。

2.2 PreToolUse 可以改参，审批以改后值为准

Hook 是配置在某个执行时点的扩展程序。运行在工具之前的 PreToolUse 可以交回一份改过的参数。假设 edit-42 原本要改 pricing.txt，改参后要处理 draft/pricing.txt。如果先批准原文件再切换执行目标，这次决定就批错了对象。程序等前置扩展和参数检查结束，再用实际要执行的参数作裁决。Hooks 篇会用完整参数与漏字段两份材料推演改参过程。

Hook 的 deny 可以拦住调用，ask 会将原本可继续且未被拒绝的调用推向人工确认。Hook 的 allow 在某些非敏感、可分析的 ask 路径可以促成允许，它不能翻转 deny。自动模式下启用的审批分类器也只参与满足条件的 ask，危险或强制人工的请求仍问用户；分类失败会转给人工，批准回复缺项按拒绝处理。更多改参、回执与回包规则见Hooks 章节。

05

学习效果检测

5.1 定位是哪个关口改变了结果

1．同一普通 Edit 同时命中 deny 和 allow，Hook 给 allow，工具会开始吗？

展开详答

调用授权先得到 deny；Hook 的 allow 只可能作用在符合条件的 ask 上。原调用收到拒绝反馈，处理器不会开始。

2． 一份旧请求在普通模式发出，当时工具清单有 Edit，用户也同意了那次改动。等轮到派发，程序已切到只做规划的 plan 模式，文件仍是原值。审查记录时，该先看哪一刻的模式？这份旧批准能证明文件写过吗？

展开详答

先查派发前复核时的实际模式。当前处于 plan，写工具在执行关口受到限制。旧清单说明当时能提出这个调用，旧批准记录当时的决定，文件现值也不能证明处理器执行过。沿原调用 ID 找派发结果，向用户说明本轮停止在哪一步。

3．工具批次审批等待中取消回合，随后 UI 返回同意。读 authorize_batch 的片段，找出结果给谁、处理器是否开始。

展开详答

批次在同一个调用 ID 上记取消消息。这个 ID 已在结果集合，后续派发会跳过它；旧批准无法启动那次调用。

模拟面试官提问

6.1 Agent 开发实习

独立核心题

模型说工具有权限，为什么编辑还是失败？你如何帮用户定位？

展开参考回答

我会从调用反馈找真正拦住的位置。合法参数可以进入权限判断；模式、规则和批准决定能否开始。进入文件工具后还要核对实际路径与读过的内容。比如用户同意编辑却没有外部写许可，应该解释目标位置，而不是让模型重填相同 JSON。

executeToolBatch 处理调用授权，approvedPath 按当前目录和路径策略进入相应文件访问判断。

重点追问链

文件移到子目录后该检查什么？

展开主问回答

先确认相对路径是否以当前 cwd 解释，以及改后调用到底审的是哪个路径。

追问 1 指向外部位置的别名会怎样？

展开追问 1 回答

检查真实目标的包含关系和适用的外部写或沙箱限制。

追问 2 有写许可但重新读到原文变了呢？

展开追问 2 回答

再次读取并重新构造匹配原文。旧批准不能恢复过期的内容基线。关联文件编辑可靠性。

6.2 Agent harness 岗位

独立核心题

如何避免一个晚到的授权响应覆盖状态已经变化的回合？

展开参考回答

我会让调用 ID 关联批准结果，再在从等待醒来、实际派发和进入处理器前核对当前模式及取消信号。只有三个条件仍有效才开始有副作用的操作。这样即使对话或批准界面与执行异步，也能守住用户刚切换的边界。

具体证据是批授权返回后的信号分支、stop_reason 及落盘意图后的再次检查。

重点追问链

如果此前只过滤 API 清单呢？

展开主问回答

清单来自早前的请求，旧响应仍可携带工具。派发必须看当前状态。

追问 1 Hook 在批准前更换了路径呢？

展开追问 1 回答

以 Hook 改写的参数重新校验并授权，权限显示和实际派发都看最终参数。

追问 2 如果信号到来时写入已开始呢？

展开追问 2 回答

进入执行后的取消需要结算该调用的结果，不能根据延迟的 UI 回执直接假设磁盘没变化。关联在途输入、等待和批准。

07

这一篇带走什么

一次文件编辑要让最终参数经过校验和调用授权，派发前确认运行状态，再由文件工具按实际目标路径落实写入边界。

  • 让批准看到实际执行参数。Hook 改参后按改后值校验、匹配规则和派发，省下原值与执行值不一致的歧义。
  • 只读规划要在请求清单与执行关口都落地。等待批准之后用当前取消信号和模式复核，迟到响应可能已经越过本轮的执行窗口。
  • 工具调用放行后，文件工具仍要解析真实目标并核对该位置的读写许可，再独立验证编辑基线。出错时沿这几类证据定位。

这次取消发生在派发之前，工具可以明确回报“未执行”。还有一种更早的中断发生在模型响应尚未收齐时。下一篇比较断流前有没有有效产出，再决定是否重新请求模型。
