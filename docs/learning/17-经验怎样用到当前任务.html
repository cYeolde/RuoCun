经验怎样用到当前任务

启动、召回、适用判断与检查

修过一次的命令值得记下来。下次拿到这条经验时，先判断它指向的还是不是同一份代码，再看手上的检查能证明什么。

01

一个跑绿的检查，为什么可能没覆盖旧错？

你让 RuoCun 修会员订单预览。历史经验建议跑 tests/test_discount.py 中的预览测试。模型照做，拿到退出码 0。把用户要验的行为和工具刚验的调用摆在一起，找出这次少测了哪个入口。

首读自检 · 现在能给“本次预览通过”打勾吗？

旧入口的断言通过了。本次应从页面调用或路由找到 preview_total，确认测试确实走它，并断言同一个会员输入在预览输出中得到 90。检查身份取决于实际调用路径和断言，测试文件名和退出码只能提供其中一部分。

直接套用旧经验时，最早出错的地方是选了旧入口的测试。退出码可以完全正确，会员页面仍可能显示 100 元。RuoCun 的记忆是从以前任务留下的文字记录，可以带到新会话。harness 先把可能有用的记录交给模型，再提示适用条件或来源变化，帮助模型选准下一步该验的入口。

02

启动快照的正文与索引

2.1 启动文本和版本身份来自同一次读取

首条 system 的材料里已经有一份启动记忆。它的内容在这里决定。程序从绑定的记忆库取项目、用户和知识库记录，作用域标明记录属于哪一类。同名记录可能分别存在于不同作用域。知识库条目的 origin 记录其来源项目，程序会用工作区根目录名称规范化得到的项目名核对它。若折扣经验来自另一个项目且没有锁定，启动筛选会跳过它。

src/ruocun/memory/store.py · 第 77–82 行

过滤后，有效条目少于 50 时启动文本放全文。到 50 条时，正文以 40 条为普通容量，剩余挑至多 200 个名称或标题进入索引。正文优先保留用户、反馈和锁定记录，这些保护项多时可以超过普通容量。普通项按重要性与使用时间评分排序。索引只给人和模型一个检索入口，缺少的条件仍要打开正文查。

src/ruocun/memory/inject.py · 第 127–135 行

src/ruocun/memory/inject.py · 第 145–152 行

text 是参与首条 system 装配的字符串。full_entries 和 index_entries 则记下作用域、记录名和对应的内容哈希。这里的哈希是把文件字节算成的短标识，可用来核对版本。分两次读取时，文档若在中间更新，旧正文可能被记成新版本。两份值来自同一次读取，后面才能准确回答启动时到底看过哪一版。

2.2 来源哈希提示文件变化

记忆文档和它引用的源码文件各有自己的内容哈希。前者核对经验原文的版本，后者核对经验写下时文件的版本。例如 preview.py 从旧入口切到新入口，记忆正文一字未改，程序仍能通过源码哈希发出变化提示。

src/ruocun/memory/validate.py · 第 27–40 行

stale 表示过期日期已过，或工作区内的文件来源无法读取，自动召回会跳过。changed 仍可供参考，但文本会附上来源已变的提示。ok 还包含没有文件来源、来源是用户陈述或无法比较摘要等情形，表示这项检查没有发现过期。依赖版本、运行配置或调用者的变化可能不在这份文件里，仍须实地核对。

03

交互输入边界的三条路径

3.1 任务召回和旧错检查随当前输入提交

输入消费处负责把一条已排队的消息写进会话。调度器取到它时，可先由绑定在输入提交事件上的 Hook 检查是否放行。只有放行才拿当前文字取词，在记忆库按范围与来源过滤，再按文本、标题等词项匹配排序。会员预览可能命中 preview_total 或“会员折扣”。词项相近只帮模型挑材料，实际版本和业务条件由模型用当前证据核对。

src/ruocun/agent/runtime.py · 第 1288–1304 行

当前路径模型这轮额外看到什么
startup默认使用启动快照。受控学习关闭时无额外按任务自动召回。
task按当前任务找记录，排除启动已给全文的作用域与名称组合。最多 2 条，全段 2400 字符，超限的整条跳过。
controlled启用受控积累的交互路径优先提供旧错检查，从语义和做法类记忆中选最多 2 条，全段 2400 字符。已给全文的同版本仍可被选为本次核对对象，补充中给定位摘录和必要警告。记忆文档有新版时，合适的条目可提供当前正文。

--memory-strategy 的选择是 startup 或 task。controlled 是另一个独立选项 --memory-learning 的值，默认关闭，受控路径用于符合条件的交互回合。--no-memory 禁用这些自动路径，评估模式也会设置该选项。召回为空时不追加补充。命中时，在会话事务里保留原用户文本，并将补充作为后续 system 消息保存。稳定的启动消息不用为了这个任务重建。

src/ruocun/session/conversation.py · 第 246–259 行

3.2 只在记忆同版时省去重复正文

设启动时已提供会员折扣经验全文。M1 代表那份 Markdown 的内容哈希，S1 是这条经验记录的源码哈希。受控旧错检查已选中同一条记录，假设以下两种情况均符合召回预算，先判断每次要不要再给全文，再单独判断要不要提示来源变化。

核对两份补充消息会带什么

甲仍是 M1，给定位摘录，同时提示 S1 与 S2 不同。乙变成 M2，可给新全文，其绑定的 S2 与当前文件一致，这一次没有来源已变警告。来源一致仍要核对测试入口和实际断言。

src/ruocun/memory/retrieval.py · 第 165–187 行

same 比较同作用域同名记录的 Markdown 哈希，verdict 来自源码来源校验。如果光按名称去重，甲的警告和乙的新做法都会漏掉。若逻辑只会重复全文，又挤占了这个回合的输入。「同一条经验的全文可以省，当前来源变化的提醒要留下」。这样做需要保存启动实际提供过的版本，也仍受词项覆盖和字符预算限制。

04

从命中走到实际检查

4.1 MemoryRead 与 MemoryWrite 操作绑定的记忆库

只看见标题时，可用 MemoryRead 查正文。对 {"query":"会员折扣预览"}，程序先按原样比对名称或标题，命中则回正文。否则做按空白拆词的关键词匹配，默认最多列 6 条，单条命中回正文，多条命中回索引式列表。这个工具读取当前绑定库里的内容，适用性仍要自行核对。它使用自己的匹配逻辑，自动召回的范围、排序与校验不能套用到这条手动路径。

src/ruocun/tools/memory_read.py · 第 27–43 行

有了稳定新做法后，可以在用户允许的范围显式写入。比如 {"title":"会员预览回归","text":"预览走 preview_total 时，断言会员实付价。","type":"semantic","scope":"project","source":"pricing/preview.py"}。MemoryWrite 会检查疑似密钥，根据显式 scope 或类型路由选择存储层，文件来源可记录摘要。删除走 delete: true 并用标题或文本定位。工具只能删原生可写条目，只读兼容条目保留。写入工具的成功回包说明条目保存，业务检查仍要另做。

src/ruocun/tools/memory_write.py · 第 39–54 行

4.2 最后一次相关修改之后再核对旧错

把本例的经验转为三个动作。先读当前预览路由确认入口。随后将“当前会员预览检查”放入现有 TodoWrite 清单，保留其他待办。测试要让输入 100 和会员身份走 preview_total，断言实付价 90。完成后用最后一次相关修改之后的工具结果报告：“旧入口检查通过，实际预览断言失败”或“当前预览断言通过”。如果测试需要的环境起不来，标未验证；新任务改到了订单结算且与旧预览无关时，可以标不适用。

src/ruocun/memory/retrieval.py · 第 35–44 行

这段约定给执行模型安排一次复验。「最新相关修改之后，检查实际入口和旧错断言」。只剩摘要和待办勾选时，用原工具调用和归档页核对证据，缺证据就标未验证。一次召回或通过也不会自动更新旧条目。下一次可被召回的新经验还得单独通过发布核对。

05

学习效果检测

5.1 判断召回内容和旧错检查结果

1． 受控召回已选中一条曾在启动时展示全文的经验。启动时正文哈希为 M1，今天是 M2；这条新记录仍绑定源码 S1，磁盘却已是 S2。假定在预算内，本次该给模型哪份文字，要保留什么提醒？拿它指导测试前先查哪儿？

展开详答

正文变了，可以给 M2 的当前内容。同一条记录还绑定 S1，来源已变的提醒也要保留。先用当前入口和断言核对 S2 上适用的做法，再跑针对性验证。展示的新正文和来源是否匹配是两项独立判断。

2．反例 · 全量测试通过，旧回归用例还没迁移，报告哪种结果？

展开详答

这次旧错检查仍是未验证。可以报告确实执行并通过的测试，另说明没有找到覆盖当前入口的特定断言。补齐后再用修改后的真实输出更新结论。

模拟面试官提问

6.1 Agent 开发实习

独立核心题

怎么让 Agent 少犯以前修过的错？

展开参考回答

“先把有关经验当检索线索，读当前入口和条件，再把最小复验并入待办。交付时报告覆盖这个错误的实际断言和结果。”本例要查预览路由并验证会员价格。条件变化、没有环境或检查失败，分别按实际结论报告。

重点追问链

只有一条标题时怎么用？

展开主问回答

“我会先精确查询该标题，取到正文和来源再决定是否需要验证。”

追问 1 找出多个命中怎么办？

展开追问 1 回答

依次按名称精确读，定位实际条件。

追问 2 如果文件提示变动呢？

展开追问 2 回答

先读新代码追实际调用，再决定是否改检查。

追问 3 上次会话只剩勾选呢？

展开追问 3 回答

沿已绑定归档查证，不能确认时报告未验证。

6.2 Agent harness 岗位

独立核心题

为什么把任务召回放在输入消费边界？

展开参考回答

“到消费边界已经知道要处理哪条用户消息，也知道输入 Hook 是否放行。此时查当下的记忆版本，将补充和本条消息一同提交。”原输入保留，启动上下文保持稳定，召回成功也不会形成新的授权。

重点追问链

如何减少重复文本又保留正确版本？

展开主问回答

“启动时一起产出文本和版本身份。任务召回时要对照当时实际看过的正文。”

追问 1 同名、不同作用域能合并吗？

展开追问 1 回答

任务去重按作用域与名称组合。

追问 2 内容相同而源文件变化怎么办？

展开追问 2 回答

受控补充仍携带警告。

追问 3 两份记忆文档的哈希相等，可以直接确认本次复验通过吗？

展开追问 3 回答

它只检查一份文档的同一性，运行入口与实际断言还得另外核对。

07

这一篇带走什么

启动快照先给模型记忆正文或索引，任务边界再找相关记录，执行模型核对现状并用针对性检查交付结果。

  • 同一段文字要跟身份一起记录。后续比较用当时读到的 Markdown 版本，引用文件的变动则用源码摘要独立提醒。
  • 词项命中时先核作用域、版本和当前调用路径，再决定旧做法是否适用。
  • 交付通过时指出最后相关修改后的具体断言。只有索引、勾选或一般测试结果时，先补能覆盖旧错的证据。
