前缀缓存怎样配合请求

稳定布局、摘要与命中观察

并排看正常请求、两种摘要请求和压缩后的请求，学会用首处变化和命中用量解释发生了什么。

01

两次请求的 system 一样，为什么缓存用量会变？

归档里的原文序号用来找回某一次操作的证据。发送模型请求时，还要看发送过去的输入从开头连续相同了多长。模型服务可能保留这段输入已经算出的中间状态。服务端通常将其中的键和值称为 KV，复用这部分计算就是这里讨论的前缀缓存。

定价会话刚跑完一组长检查。下一次切到工作树，仍用同一模型和工具，程序在历史末尾补了一条新的目录说明。再下一次请求前，工具列表的顺序变了。三次请求的 system 文字一样。把工具数组与消息数组放在各自一列，逐项比较 A 到 B、B 到 C。

示意 · 同一路由与模型下的三个请求片段
请求实际工具顺序按顺序发送的消息
A · 原目录Read → Edit同一 system → 目录 A → 已配对的测试调用和长结果
B · 切到工作树Read → Edit同一 system → 目录 A → 已配对的测试调用和长结果 → 新目录 B
C · 工具重排Edit → Read同一 system → 目录 A → 已配对的测试调用和长结果 → 新目录 B
首读自检 · A 到 B 保留了哪段连续消息？B 到 C 的第一个工具还相同吗？

A 的全部消息仍是 B 的消息前缀。B 到 C 的消息相同，但工具数组从开头就变了。只比 system 找不到任何一个差异。这些是本地对照线索，哪个请求实际命中多少还要看服务回包。

试把新目录事实放到历史开头附近。它前面仍相同，插入点之后即使还能找到一样的消息，也已经超出这段共同前缀。这就是比较位置比搜索重复文字更有用的原因。

03

同模型摘要、异模型摘要和最终投影

3.1 把摘要指令加在原始连续前缀之后

压缩篇已分清交给摘要模型的旧原文和确认后交给主模型的新历史。这里用这两份材料比较连续前缀。普通请求曾带着完整长日志，若现在先重排 Hook 或删去日志中段，摘要请求从相应位置就失去共同前缀。

示意 · 同一路由中连续消息项与工具选项如何对齐
请求有效模型与工具消息顺序
普通请求M，Read, Editsystem、Hook、测试调用和完整长日志、近期历史
同模型摘要M，Read, Editsystem、Hook、测试调用和完整长日志、末尾摘要指令
显式异模型摘要N，移除工具，采用摘要侧思考设定原始连续旧前缀、末尾摘要指令
压缩后继续主任务M，恢复本次主轮工具system、Hook、新摘要、近期历史、有效待办

在这组例子中，普通请求与同模型摘要在旧组结束处之前的消息相等。压缩后的新请求从原工具组变成摘要的位置开始不同，之后可以为新的连续历史形成缓存。同模型摘要通过深拷贝本次有效请求保留连接、工具定义及顺序、并行工具设置和已有思考模式，同时移除主轮强制工具选择及冲突的输出上限，以摘要自己的输出上限执行。显式异模型同样尊重配置，清除工具并禁用思考。对照这两种情况，要先核实实际生效模型和请求格式。

src/ruocun/agent/context_runtime.py · 第 300–322 行

假设原窗口 20,000，待摘要的原始请求估计 18,000，摘要输出上限 2,400。直接裁掉长日志中段或许放得进去，但会从那条工具消息开始改变送去摘要的连续前缀，也改变摘要实际能用的证据。RuoCun 对已经选中的摘要输入保留原文，代价是这个请求算出来要 20,400，超出窗口时保留原投影并停止。切点、候选和持久化细节见上下文压缩。

3.2 摘要沿用工具定义，处理器只接收摘要文本

如果有效主请求带工具，保留它们能尽量维持请求模式。有人会同时设置 tool_choice=none，但这会改变选择模式。RuoCun 清除主轮的强制选择，不额外强制一个新模式，在摘要返回处把关。它独立调用摘要模型，没有走工具派发循环。

src/ruocun/agent/context_runtime.py · 第 343–360 行

假设摘要模型回了一条 Read 请求。即使同名工具在请求中公布，程序也会检查完成消息、结束原因及分片，发现调用就停止。会话保留原上下文，并记录收到的用量。完整、未截断、有正文且没有工具调用的摘要才继续参与候选缩小和提交。「摘要请求可以公布工具，返回的调用仍不得进入派发」。这让保护旧前缀与控制运行行为各有自己的落点。

04

命中用量、指纹与差异位置

4.1 供应商用量回答命中多少，本地指纹帮助找到变化

要判断实际命中，读回包用量。原生 prompt_cache_hit_tokens 优先，缺该字段时尝试从 prompt_tokens_details.cached_tokens 补齐，并用 prompt_tokens 减去它估出未命中输入。输入总量为正时，审计以命中 token 除以总输入得到比率。用量字段缺失时保留观测缺口，报告默认值不能替供应商解释缓存是否启用。

src/ruocun/client/client.py · 第 183–195 行

要定位可能原因，主循环在预检后记录模型、system、工具指纹；启用审计后，有用量的轮次还可按执行身份记录各维度以及消息指纹。主循环这里使用预检后的选项和消息，摘要记录由其请求体构造器取得字段。它们是本地对照线索。检查供应商真正接到的结构时，还要核对实际外发、路由投影和覆盖项。

src/ruocun/session/cache_audit.py · 第 108–125 行

审计按 agent、子任务 ID 和深度分组比较模型、system、工具、tail 四维。本例的 CWD 在消息尾部，主轮记录的 tail 字段是空串，目录改变会影响主轮的 msgs 指纹，但未必出现在 changed 的四维列表。变动维度提供 firstDiffAt 和上下文样本，单位是 UTF-16 代码单元。比如本地比较短字符串 Read,Edit 和 Edit,Read，第 0 位就不同。实际审计比较序列化后的工具定义，首个不同位置通常在两者共同的 JSON 结构之后。msgs 的专门差异位置在 distill 对照最近主请求时计算，摘要和常规轮的完整前缀需要另行把消息项逐条对齐。

4.2 从三组数据逐步缩小解释

示意用量 · 模型和工具相同的请求也会有不同命中
请求共同输入观察输入 / 命中当前能说什么
首次普通请求作为比较基准8,000 / 0本轮报告没有命中
同模型，原前缀加摘要指令工具同序，旧消息段连续相等8,400 / 8,000本轮报告命中约 95.2%

表里第三次已经找到工具顺序变化。如果另一次四维都稳、命中率仍低，先审消息和实际外发请求，再看空闲时长。报告在四维未变、低命中、输入达到一定体量且空闲超过阈值时提示“TTL 过期”。TTL 指一份缓存能留存的时间。这里是在用本地阈值猜测缓存可能已失效，服务端没回报实际失效时间。「指纹用来找首处变化，回包用量才报告这次实际命中」。固定请求布局能增加复用机会，命中还受服务端状态影响。

项目已有一组受控渠道观察。三次首次摘要使用相同类别的合成历史，固定预热和等待条件，逐次记录同模型新路径的命中输入与总输入，分别为 28032 / 28559、28032 / 28559 和 28288 / 28766，加权约 98.22%。固定的旧摘要控制路径在这三组报告为零。这个观察支持所测请求形状和服务条件下的输入命中收益。读取摘要时仍要检验语义，成本要同时考虑输出及各自单价，见完成证据与资源取舍。

05

学习效果检测

5.1 比较请求前缀与服务回报

1．cwd 变化只追加尾部消息，应该预期 system 指纹、消息指纹怎样变化？

展开详答

旧 system 保持时它的指纹不变。目录消息改变整体消息文本，通常会改消息指纹。逐条比较可见先前消息完整保留为前缀。若另有 system 刷新或路由变化，应单独核对。

2．同模型摘要为什么读取旧长日志而不直接使用这次产生的裁剪文本？

展开详答

这次裁剪只针对压缩候选与最终投影。摘要输入要保持旧消息在切点前连续原样，上游服务才有机会复用旧前缀。原始前缀放不下时会停止。

3．摘要完整返回，正文非空，但流中曾出现工具调用分片。能提交吗？

展开详答

不能。调用分片也会触发拒绝，即使最终文本不空。摘要只接受无工具调用的完备结果，不接通执行器，主会话保持原投影。

4． 同一模型两次请求的 system、工具指纹相同。甲的服务回包给出输入 10,000、命中 8,000；乙只报告输入 12,000，没有任何缓存用量字段。同事把乙记成“命中率 0%”。你能确认哪次的比率？下一步查哪份原始数据？

展开详答

甲可算出 80%。乙只有总输入，命中量缺失，不能填作零。先查看乙的原始用量和兼容的 cached_tokens 字段；仍缺就标未知。要再调查为什么可能变化，再核对路由、模型选项、实际输入顺序和首个差异位置。共同指纹给不了服务端实测比率。

06

模拟面试官提问

6.1 Agent 开发实习

独立核心题

目录频繁变化时，怎样仍有机会复用前缀？

展开参考回答

我会把稳定的系统内容和工具定义放到一致的请求结构中，目录变化时在消息尾部追加新事实，并让程序按真实目录执行。这样已有内容可以继续保持连续，之后再看服务实际报告的命中用量。

RuoCun 只在目录事实有变化时追加。若工具或 system 同时变化，需要在各自的请求字段里另找差异。

重点追问链

一项请求布局改动的缓存效果怎样验证？

展开主问回答

我会先固定服务和模型，用同一套历史、工具、预热与等待条件对照外发结构和用量。

追问 1 换了一次 provider 后命中增加呢？

展开追问 1 回答

先按两种不同运行条件记录，不能单独归因给布局。

追问 2 稳定命中增加但延迟更长呢？

展开追问 2 回答

单独记录输出、思考模式和生成时间。输入复用有收益，但任务延迟受其他阶段影响。

6.2 Agent harness 岗位

独立核心题

如何让摘要复用主请求前缀，同时把可执行副作用留在主循环？

展开参考回答

我保持同一路由的有效模型、工具定义、模式和选定的原始连续消息。摘要指令放最后，调用方只接收摘要文本，一旦返回工具调用就停止候选发布。

摘要输出上限独立设置并执行完整请求预算检查。压缩后的正式会话投影可以重组，只要通过候选验证和持久化。

重点追问链

为什么同模型摘要仍可能没命中？

展开主问回答

我先验证实际外发的前缀、工具模式和回包用量，再检查可复用材料占比和服务条件。

追问 1 提示低命中和空闲过久，能否说服务端 TTL 是五分钟？

展开追问 1 回答

不能从这个数据推断，提示阈值只是本地诊断口径。

追问 2 如果共同前缀确实很长，但最终压缩请求的命中降低呢？

展开追问 2 回答

查候选提交后旧组替换成摘要的第一处变化，这是与摘要本身独立的请求。

07

这一篇带走什么

稳定的请求布局保留可复用的连续前缀，摘要沿用原始旧段，压缩后用提交过的新投影继续，并由服务回包反映实际命中。

  • 把变化频繁的目录事实追加在尾部。比较时固定有效模型和路由，再查看工具定义顺序、系统内容和完整消息前缀。
  • 需要复用摘要前缀时保留实际请求模式，把工具执行留给明确的派发路径。摘要调用用自己的预算检查和纯文本结果门槛。
  • 用回包用量度量命中，用指纹和首差定位本地变化。推断原因需要控制请求条件，质量、延迟和费用各自核对。

缓存复用的是已经计算的输入。到了新任务，程序还可以从记忆库找相关记录。下一篇用一条旧测试建议，看看哪些经验值得带进新请求。
