任务在跑时用户又说话

输入排队、等待、批准与取消

跟着“保留日志”这句补充，看它什么时候被接纳，什么时候进入模型请求，以及暂停怎样挡住旧回合。

01

“保留日志”能插进正在执行的工具批次吗？

上一篇第 8 版检查点已经保存了“保留日志”。现在回到用户刚输入这句话的时刻。模型刚在同一条助手消息里发出 q-test 和 q-style 两次日志查询。第一条结果先到，用户输入居中，第二条结果随后到。终端显示“收到”时，第二项查询还没返回。沿时间往下读，同一句话先后出现在哪里？

停在第二行，重开后从哪里找这句话？能立刻让模型接着答吗？

按输入 ID 查账本能找回这句话。已发送的请求看不到它。先核对并补齐原工具组，到可消费输入的边界时，才把用户消息和消费状态一起保存。把补充直接夹在两个回包之间，会拆散同一助手消息的调用与结果。

如果只把新输入暂存在界面，程序退出时这句话就丢了。RuoCun 要维护两笔状态来允许用户及时说话。一笔负责记录“已经接纳”，另一笔负责确认“可以交给模型”。这句补充与后面答复“保留原始日志还是摘要”也分属不同入口，后一项要回到正在等答案的工具调用。

02

接纳账本与消费边界

2.1 接纳先保存 ID 和顺序，消费再更新模型历史

Conversation.queue_user 在检查点锁内给输入分配唯一 ID（UUID）、下一个顺序号 seq 和 queued 状态，连同当时的检查点保存。数据库确认后才返回接纳回执。把“保留日志”重新发一遍，一般会留下另一个输入 ID，模型读取过哪一次要按各自的编号确认。此时模型消息保持原样，工具结果仍可按原批次收齐。

src/ruocun/session/conversation.py · 第 220–230 行

调度器启动一次执行前，或同一回合下一次发模型请求前，会进入 _boundary。这是可以取新材料、调整下一次请求的时点。它为当前活动回合按 seq 取已接纳队列里最早的一项，并投递此时可处理的后台事件。若配置了输入 Hook，程序还会在用户输入即将进入模型历史的时点执行规则。被规则拒绝的输入保存为 discarded，原始记录可查，该输入不会变成模型消息。

src/ruocun/session/conversation.py · 第 239–259 行

读上面这段，把输入 input-log 代进去。它必须仍是队首且未被消费；助手调用少一条工具结果时，_require_paired 拒绝更新。满足条件后构造用户消息与变更后的输入账本，两个状态一起提交，确认后才换内存中的 session.messages。这样重新打开时，既不会消耗了输入却没有用户消息，也不会为一个已消费的 ID 又追加一遍。「接纳输入先入账，在消息配齐的边界再原子消费」。

03

运行代际与暂停

3.1 暂停先更新代际，旧回合才能放心收尾

运行代际 generation 是调度器给整个活动回合的编号。一次 _pump 启动时取一个新编号和独立取消信号；调度器靠编号核对增量、输入消费及执行完成是否仍属于当前回合。同一回合可以先后发多次模型请求，各有自己的请求令牌。这样既能挡一次模型请求结束后的旧显示，也能撤销暂停前整个回合推进会话的资格。数据库 owner_epoch 则在进程接管时变化，仍负责核对写入者。

src/ruocun/agent/session_scheduler.py · 第 141–143 行

设活动回合是第 12 代。取消信号置位后，在途异步任务仍可能回到调度器，例如恰好带来一个刚登记好的等待句柄。若完成回调直接写状态，这份迟到结果会把暂停会话改回 waiting。以下按时间看，回调到底属于谁。

检查失败，调度器让旧任务收尾，跳过等待激活。只有取消信号很容易漏掉已经排进事件循环的正常回调。编号检查多保留一份运行身份，换来回包再晚也只能属于它原来的回合。暂停自己的队列处置回执返回时也要核对编号。

src/ruocun/agent/session_scheduler.py · 第 263–277 行

src/ruocun/agent/session_scheduler.py · 第 352–373 行

暂停会显式将仍排队的输入标为 discarded，已消费的留下；可以接受新输入走下一代。调度器关闭时则拒绝再接纳。代次和取消信号解决“谁还能驱动当前会话”。在它们之外，已经开始的工具还需要结算真实副作用，转交后台的运行也按自己的控制状态管理。

3.2 等待句柄交给调度器，前台先让出

上面的 waiting 是主循环向调度器交还前台时的状态。随它返回的等待句柄 handle 是一份已登记的等待约定，写明本会话等哪些后台运行、什么条件算就绪。代码通过代际检查后才激活它。后台运行继续做事，新输入或就绪事件到来后，调度器会安排新的工作。

04

用户问答与方案批准

4.1 AskUserQuestion 把用户决定写回工具结果

“保留日志”已经作为新输入进入历史，现在要决定保留哪些内容。原始日志便于审查，摘要占用空间更小。这里的回答属于已发出的提问工具：模型收到的是与该次提问配对的 tool 消息。旁边聊天框里新发的一句话则沿前面的队列进入历史。

有选项且交互回调可用时展示选择，否则使用普通询问入口；没有必要的询问能力则报告不支持。多问题依次询问，用户选“先讨论”后，剩余问题会标记未问。等待问答的回合收到取消信号时，工具将结果标为中断。

src/ruocun/tools/ask_user.py · 第 26–35 行

4.2 退出 plan 只改变会话模式，具体工具仍需授权

如果还要设计日志保留方案，EnterPlanMode 可以进入只读探索；有模式绑定且环境可交互时才设置 plan，无人值守入口拒绝这次切换。ExitPlanMode 有选择回调时问用户是否批准；未批准则继续规划，没有选择回调时处理器沿现有实现直接设置 normal。模式切换改变工具清单和派发限制。

src/ruocun/tools/plan_mode.py · 第 8–25 行

模型调用 ExitPlanMode 时传入 {}。比如用户同意只保留失败摘要，会话可以退出规划模式。接下来模型发出的 Bash 调用仍走第 8 篇的实际派发关口，由权限层按具体命令、路径和当前模式作出裁决。「方案获准与具体动作获准分别确认」。

05

学习效果检测

5.1 追踪队列、旧回合和人的决定

1． 输入账本里 u17 为 queued，u18 为 discarded；历史还欠原工具组一条结果。有人建议把两句话都粘到历史末尾。哪些证据能说明它们已被模型看到？重开后应该先处理谁？

展开详答

这两种状态都不能证明本次模型请求已带上相应文字。先核对并修复原工具组的配对，再在可消费的边界按队列检查 u17 是否获准，成功时连同用户消息原子提交。u18 已丢弃，应保留原记录。最终要用实际外发的消息列表核对模型能看到哪句话。

2．调度器暂停第 12 代，原来等的确认随后返回。哪些条件使这次结果无法把调度器恢复到 running？

展开详答

暂停先增加当前代次，使原 12 无法通过代次相等条件，同时改变状态和置取消信号。存储或工具若已有实际结果可按自己的承诺结算，旧回调无权启动新一轮。

3． 设计评审 工具还在跑，用户补充“发给测试组”。界面团队想立刻回一声“收到”。你会把这句话承诺为“本机看见了”还是“重开也找得回”？选一个时机，解释程序突然退出时能兑现什么，以及用户要等什么。

展开详答

我会在输入 ID、顺序和原文保存确认后才显示“已收到”。此刻退出，重开仍能从排队记录找回原话。工具组配齐且输入获准消费后，用户消息和消费状态一起保存，再交给模型。代价是存储慢时，确认也会慢。

如果界面需要立即响应，可以先显示“正在保存”，等提交确认再改为“已收到”。这样用户看见了操作反馈，也知道此刻是否已经具备重开找回的保证。

06

模拟面试官提问

6.1 Agent 开发实习

独立核心题

用户可以一边等 Agent 一边补充要求，你怎样告诉用户这些要求到哪一步了？

展开参考回答

我会先确认输入已经接纳并排队，等当前消息处在安全边界后才消费。这样用户能分辨系统收到要求和模型已经读到要求，也能看到暂停后还有哪些要求需要重提。

RuoCun 保存输入的独立身份、顺序和状态，再把真正消费到的输入和新消息一起提交。

重点追问链

如果两句话相同呢？

展开主问回答

正常提交的输入按各自 ID 和接受顺序处理，不能只以文本判断已经消费过。

追问 1 如果用户是在回答当前的选择面板呢？

展开追问 1 回答

选择面板回复属于当前询问，经工具结果回到模型。正常聊天文本走会话排队。

追问 2 如果用户选“先讨论”呢？

展开追问 2 回答

多题询问停止向后提问，返回已取得的答案和未问状态。

6.2 Agent harness 岗位

独立核心题

用户取消后，怎样防止迟到事件推进旧回合，同时保留可信结果？

展开参考回答

我会给活动回合加代际和取消信号，投递增量、消费输入或从等待返回时核对身份。暂停时先废除旧代次，再收尾已启动动作。存储提交和工具结果依照各自的权威回执决定能保留什么。

is_current 核对整个活动回合，模型请求内部还有请求令牌，二者分别过滤迟到事件。关联模型请求恢复。

重点追问链

输入确认恰在暂停后返回怎么办？

展开主问回答

保留提交已经确认的事实，旧代次的回执无权把会话状态改回空闲。暂停动作按当前约定处置仍排队的输入。

追问 1 等待消息还没保存时能不能释放执行？

展开追问 1 回答

需要先确认该等待对应的工具消息和消费状态。保存异常时不激活未确认的 handle。

追问 2 已经提交等待后，新输入如何唤醒？

展开追问 2 回答

调度器发现等待有效且有新队列输入时释放等待，排入下一次执行；下一次在完整边界消费并读取已投递结果。关联检查点与工具恢复。

07

这一篇带走什么

前台调度以输入的接纳回执、消息安全边界和当前代际推进任务，并把已确认的等待或用户决定交回适用的执行路径。

  • 在途输入先单独按 ID 和顺序保存，历史配齐后再同消费状态提交。崩溃恢复可以从账本判定这句话该不该进入模型。
  • 取消时先吊销旧代次，再结算已经开始的动作。新会话状态和旧动作的真实结果各按自己的权威记录处理。
  • 等待需要已确认的条件，人的方案批准需要实际模式切换。具体工具仍看实时权限，避免让一条文本替代执行关口。

这一篇把 waiting 看成调度器接过的一份等待约定。下一篇先用两条同为 running 的记录辨认哪一趟运行能成为等待目标。
